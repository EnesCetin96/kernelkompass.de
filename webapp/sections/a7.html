✎ Notlarım — Dosya Sistemleri ve VFS

temel kavram "Everything Is a File": The Architectural Payoff — Çekirdeğin "her şey bir dosyadır" karşılığı— Die architektonische Einlösung von "Alles ist eine Datei"

One of the most familiar Unix principles is "everything is a file" — regular files, directories, devices, pipes, even sockets are all reachable through one common interface: open, read, write, close. The kernel component that makes this unified view possible is the VFS (Virtual File System) layer. VFS abstracts away the wildly different on-disk formats and feature sets of concrete filesystems — ext4, XFS, Btrfs, FAT, NFS, tmpfs and more — and presents user space, and the rest of the kernel, with a single, consistent system-call interface. A shell script that does cat /dev/urandom, echo hello > /dev/null, or reads a line from a named pipe never needs special-case code for "this resource is a device" versus "this resource is a regular file" — the same four verbs work everywhere.

TRUnix felsefesinin en tanıdık ilkelerinden biri "her şey bir dosyadır"dır — düzenli dosyalar, dizinler, aygıtlar, pipe'lar, hatta soketler bile ortak bir arayüz (açma, okuma, yazma, kapatma) üzerinden erişilebilir. Bu birleşik görünümü mümkün kılan çekirdek bileşeni VFS (Virtual File System) katmanıdır. VFS, somut dosya sistemlerinin (ext4, XFS, Btrfs, FAT, NFS, tmpfs…) birbirinden çok farklı disk üzeri formatlarını ve özelliklerini soyutlayarak, kullanıcı alanına ve çekirdeğin geri kalanına tek, tutarlı bir sistem çağrısı arayüzü sunar. cat /dev/urandom, echo merhaba > /dev/null ya da isimli bir pipe'tan bir satır okuyan bir kabuk betiği, "bu bir aygıt" ile "bu düzenli bir dosya" ayrımı için hiçbir özel kod yazmak zorunda kalmaz — aynı dört fiil her yerde çalışır.

DEEines der bekanntesten Unix-Prinzipien ist "Alles ist eine Datei" — reguläre Dateien, Verzeichnisse, Geräte, Pipes, sogar Sockets sind über eine gemeinsame Schnittstelle erreichbar: öffnen, lesen, schreiben, schließen. Die Kernel-Komponente, die diese einheitliche Sicht ermöglicht, ist die VFS (Virtual File System)-Schicht. VFS abstrahiert die stark unterschiedlichen Formate und Funktionsumfänge konkreter Dateisysteme — ext4, XFS, Btrfs, FAT, NFS, tmpfs und mehr — und bietet dem Userspace sowie dem Rest des Kernels eine einzige, konsistente Systemaufruf-Schnittstelle. Ein Shell-Skript, das cat /dev/urandom, echo hallo > /dev/null ausführt oder eine Zeile aus einer benannten Pipe liest, braucht nie Sonderfall-Code für "das ist ein Gerät" versus "das ist eine reguläre Datei" — dieselben vier Verben funktionieren überall.

Contrast this with an operating system that lacked such an abstraction: every subsystem — networking, device drivers, inter-process communication — would need its own bespoke API, and every application would need to know in advance which API to call for which resource. VFS's genius is architectural, not algorithmic: it defines a contract (a set of operations every concrete filesystem must implement — open, read, write, lookup, and more) and then dispatches through function pointers to whichever filesystem actually owns the resource. The caller never needs to know or care which one that is.

TRBunu, böyle bir soyutlamadan yoksun bir işletim sistemiyle karşılaştır: ağ, aygıt sürücüleri, süreçler arası iletişim gibi her alt sistem kendi özel API'sine ihtiyaç duyardı ve her uygulama, hangi kaynak için hangi API'yi çağıracağını önceden bilmek zorunda kalırdı. VFS'nin dehası algoritmik değil mimaridir: bir sözleşme tanımlar (her somut dosya sisteminin uygulaması gereken bir işlem kümesi — open, read, write, lookup ve daha fazlası) ve ardından fonksiyon işaretçileri üzerinden isteği, kaynağı gerçekten sahiplenen dosya sistemine yönlendirir. Çağıran taraf bunun hangi dosya sistemi olduğunu asla bilmek ya da umursamak zorunda değildir.

DEMan vergleiche das mit einem Betriebssystem ohne solche Abstraktion: jedes Subsystem — Netzwerk, Gerätetreiber, Interprozesskommunikation — bräuchte seine eigene, maßgeschneiderte API, und jede Anwendung müsste vorab wissen, welche API für welche Ressource zuständig ist. Das Geniale an VFS ist architektonisch, nicht algorithmisch: es definiert einen Vertrag (eine Menge von Operationen, die jedes konkrete Dateisystem implementieren muss — open, read, write, lookup und mehr) und leitet die Anfrage dann über Funktionszeiger an das Dateisystem weiter, das die Ressource tatsächlich besitzt. Der Aufrufer muss nie wissen oder sich darum kümmern, welches das ist.

💡 Tip: next time cat /dev/urandom or a pipe redirect "just works" without any special flags, that's VFS silently dispatching the same open/read/write calls it would for a plain text file.
💡 İpucu: cat /dev/urandom ya da bir pipe yönlendirmesi hiçbir özel bayrak olmadan "kendiliğinden çalıştığında", bu VFS'nin sıradan bir metin dosyası için yapacağı aynı open/read/write çağrılarını sessizce yönlendirmesidir.
💡 Hinweis: wenn cat /dev/urandom oder eine Pipe-Umleitung ohne besondere Flags "einfach funktioniert", leitet VFS im Hintergrund dieselben open/read/write-Aufrufe weiter wie bei einer gewöhnlichen Textdatei.

mimari nesneler VFS's Four Core Objects — VFS'nin dört temel nesnesi— Die vier Kernobjekte des VFS

VFS is organized around four central data structures. The superblock holds metadata about a mounted filesystem as a whole (its type, size, state) — every mounted filesystem has exactly one. The inode (index node) holds metadata about a single file: ownership, permissions, size, timestamps, and the on-disk location of its data blocks. The critical point: an inode does not carry the file's name. The dentry (directory entry) is the object that binds a filename to an inode — and more than one dentry can point at the same inode, which is exactly how hard links work. The dentry cache (dcache) aggressively caches this binding to speed up path resolution, so that a path like /usr/local/bin/foo doesn't require re-reading every component from disk on every lookup — recall §6.3's dentry-leak case, where a runaway dcache was the actual memory hog. Finally, the file object represents a process's per-open state of an open file: its current read/write offset and open flags. If the same file is opened multiple times — by different processes, or the same process twice — each open gets its own file object, but all of them point at the same inode.

TRVFS, dört merkezi veri yapısı etrafında organize edilir. superblock, mount edilmiş bir dosya sisteminin bütününe ait meta veriyi (türü, boyutu, durumu) tutar — her mount edilmiş dosya sisteminin tam olarak bir superblock'u vardır. inode (index node), tek bir dosyanın meta verisini tutar: sahiplik, izinler, boyut, zaman damgaları ve veri bloklarının disk üzerindeki konumu. Kritik nokta: bir inode dosyanın adını taşımaz. dentry (directory entry), bir dosya adını bir inode'a bağlayan nesnedir — ve aynı inode'a birden fazla dentry işaret edebilir, sabit bağların (hard link) tam olarak nasıl çalıştığı budur. Dentry önbelleği (dcache), yol adı çözümlemesini hızlandırmak için bu bağı agresif biçimde önbelleğe alır; böylece /usr/local/bin/foo gibi bir yol, her aramada her bileşenin diskten tekrar tekrar okunmasını gerektirmez — §6.3'teki dentry sızıntısı vakasını hatırla, orada asıl bellek yiyicisi kontrolsüzce büyüyen dcache idi. Son olarak file nesnesi, açık bir dosyanın süreç bazındaki durumunu temsil eder: mevcut okuma/yazma konumu (offset) ve açılış bayrakları. Aynı dosya birden fazla kez açılırsa — farklı süreçler tarafından ya da aynı süreçte iki kez — her açılış kendi file nesnesini alır, ama hepsi aynı inode'a işaret eder.

DEVFS ist um vier zentrale Datenstrukturen organisiert. Der Superblock hält Metadaten über ein gesamtes gemountetes Dateisystem (Typ, Größe, Zustand) — jedes gemountete Dateisystem hat genau einen. Der Inode (Index-Node) hält Metadaten über eine einzelne Datei: Eigentümer, Berechtigungen, Größe, Zeitstempel und die Position ihrer Datenblöcke auf der Platte. Entscheidend: ein Inode trägt nicht den Dateinamen. Der Dentry (Directory Entry) ist das Objekt, das einen Dateinamen an einen Inode bindet — und mehr als ein Dentry kann auf denselben Inode zeigen, genau so funktionieren Hardlinks. Der Dentry-Cache (dcache) cacht diese Bindung aggressiv, um die Pfadauflösung zu beschleunigen, sodass ein Pfad wie /usr/local/bin/foo nicht bei jeder Suche jede Komponente erneut von der Platte lesen muss — man erinnere sich an den Dentry-Leck-Fall aus §6.3, wo ein außer Kontrolle geratener dcache der eigentliche Speicherfresser war. Schließlich repräsentiert das File-Objekt den prozessbezogenen Zustand einer geöffneten Datei: aktuelle Lese-/Schreibposition und Öffnungsflags. Wird dieselbe Datei mehrfach geöffnet — von verschiedenen Prozessen oder demselben Prozess zweimal — erhält jede Öffnung ihr eigenes file-Objekt, doch alle zeigen auf denselben Inode.

Real-world case — disk is full, but df and du disagree: a system administrator finds df -h reporting the disk 98% full, but summing directories with du -sh /* doesn't account for anywhere near that much space. Running lsof | grep deleted reveals the culprit: a log file was removed with rm by a log-rotation script, but the application still holds the old file descriptor open (the rotation script opened the new file without closing the old one first) — since the inode's reference count never dropped to zero, its data blocks are still occupying disk space that no directory listing will ever show. The fix is to restart the application (releasing the file descriptor) or to truncate the file directly through /proc/<pid>/fd/<fd-number> (with > /proc/<pid>/fd/<n>). This case proves that the inode/dentry distinction isn't a purely academic detail — it's a direct operational fact any Linux administrator eventually runs into.

TRGerçek olay örgüsü — Disk dolu ama df ile du uyuşmuyor: bir sistem yöneticisi, df -h çıktısının diskin %98 dolu olduğunu gösterdiğini, ama du -sh /* ile dizinleri topladığında bu kadar alanın hiçbir yerde görünmediğini fark eder. lsof | grep deleted komutu suçluyu ortaya çıkarır: bir log dosyası, rotasyon script'i tarafından rm ile silinmiştir ama uygulama hâlâ eski dosya tanımlayıcısını açık tutmaktadır (rotasyon script'i yeni dosyayı, eskisini kapatmadan açmıştır) — inode'un referans sayısı hiçbir zaman sıfıra inmediği için, veri blokları hiçbir dizin listelemesinde görünmeyen disk alanını işgal etmeye devam etmektedir. Çözüm, uygulamayı yeniden başlatmak (dosya tanımlayıcısını serbest bırakmak) ya da dosyayı doğrudan /proc/<pid>/fd/<fd numarası> üzerinden (> /proc/<pid>/fd/<n> ile) truncate etmektir. Bu vaka, inode-dentry ayrımının salt akademik bir ayrıntı olmadığını — her Linux yöneticisinin er ya da geç karşılaşacağı doğrudan operasyonel bir gerçek olduğunu kanıtlar.

DERealer Fall — Platte ist voll, aber df und du stimmen nicht überein: ein Systemadministrator stellt fest, dass df -h die Platte zu 98% voll meldet, aber das Aufsummieren von Verzeichnissen mit du -sh /* diese Menge nirgends erklärt. lsof | grep deleted deckt den Übeltäter auf: eine Logdatei wurde von einem Rotationsskript mit rm gelöscht, aber die Anwendung hält den alten Dateideskriptor weiterhin offen (das Rotationsskript öffnete die neue Datei, ohne zuerst die alte zu schließen) — da der Referenzzähler des Inodes nie auf null fiel, belegen seine Datenblöcke weiterhin Plattenspeicher, den keine Verzeichnisauflistung je zeigen wird. Die Lösung: die Anwendung neu starten (Dateideskriptor freigeben) oder die Datei direkt über /proc/<pid>/fd/<fd-Nummer> (mit > /proc/<pid>/fd/<n>) leeren. Dieser Fall beweist, dass die Inode/Dentry-Unterscheidung kein rein akademisches Detail ist — sondern eine direkte operative Tatsache, der jeder Linux-Administrator irgendwann begegnet.

💡 Tip: whenever df and du disagree, check lsof | grep deleted before you go hunting for phantom files — it's almost always an open handle to something already unlinked.

karşılaştırma Filesystem Types and Mount Persistence — Dosya sistemi türleri ve mount kalıcılığı— Dateisystemtypen und Mount-Persistenz

Linux supports many concrete filesystem types, each trading off differently: ext4 has been Linux's default for years, offering journaling (crash resilience) with mature, predictable performance. XFS is high-performance, strong with large files and parallel I/O, and common in enterprise storage. Btrfs is a modern copy-on-write filesystem offering snapshots, built-in RAID-like features, and data-integrity checksums. tmpfs lives entirely in memory (and swap if needed) and is non-persistent — /tmp and /dev/shm are typically mounted as tmpfs, making them RAM-speed but gone on reboot. overlayfs is a union filesystem that merges several directories into one logical view — the foundation of container image layering in Docker and containerd.

TRLinux, her biri farklı bir takas sunan pek çok somut dosya sistemi türünü destekler: ext4, uzun yıllardır Linux'un varsayılanıdır — günlükleme (journaling) ile ani kapanmalara dayanıklılık sağlar, olgun ve öngörülebilir bir performansa sahiptir. XFS yüksek performanslıdır, büyük dosyalar ve paralel G/Ç'de güçlüdür, kurumsal depolama sistemlerinde yaygındır. Btrfs, anlık görüntü (snapshot), yerleşik RAID benzeri özellikler ve veri bütünlüğü kontrol toplamları (checksum) sunan, copy-on-write tabanlı modern bir dosya sistemidir. tmpfs tamamen bellekte (gerekirse swap'ta) yaşar ve kalıcı değildir — /tmp ve /dev/shm genellikle tmpfs olarak mount edilir, bu da onları RAM hızında ama yeniden başlatmada kaybolan bir depolama alanı yapar. overlayfs, birden fazla dizini tek bir mantıksal görünümde birleştiren bir birleşim dosya sistemidir — Docker ve containerd'in imaj katmanlama mekanizmasının temelidir.

DELinux unterstützt viele konkrete Dateisystemtypen, jeder mit anderen Kompromissen: ext4 ist seit Jahren Linux' Standard, bietet Journaling (Crash-Resilienz) mit ausgereifter, vorhersagbarer Leistung. XFS ist hochperformant, stark bei großen Dateien und paralleler I/O, verbreitet in Unternehmensspeichern. Btrfs ist ein modernes, Copy-on-Write-basiertes Dateisystem mit Snapshots, eingebauten RAID-ähnlichen Funktionen und Datenintegritäts-Prüfsummen. tmpfs lebt vollständig im Speicher (bei Bedarf im Swap) und ist nicht persistent — /tmp und /dev/shm werden typischerweise als tmpfs gemountet, was sie RAM-schnell, aber beim Neustart verloren macht. overlayfs ist ein Union-Dateisystem, das mehrere Verzeichnisse zu einer logischen Ansicht verschmilzt — die Grundlage der Container-Image-Schichtung in Docker und containerd.

Manually mounting a filesystem with mount /dev/sdb1 /veri only lasts for that session — the mount is gone after a reboot. Persistent mounts are defined in /etc/fstab, where each line has six fields: device identifier, mount point, filesystem type, options, dump flag, and fsck order. The options field matters most in daily practice: defaults is shorthand for the typical defaults (rw, suid, dev, exec, auto, nouser, async), noatime skips updating the access timestamp on every read (a real I/O saving on busy filesystems, since otherwise every read() quietly triggers a write), and ro mounts read-only. mount -a mounts every not-yet-mounted entry from /etc/fstab — the standard way to test an edit without rebooting.

TRBir dosya sistemini elle mount /dev/sdb1 /veri ile bağlamak yalnızca o oturum için geçerlidir — sistem yeniden başlatıldığında bu bağlama kaybolur. Kalıcı bağlamalar /etc/fstab dosyasında tanımlanır; her satır altı alandan oluşur: aygıt tanımlayıcısı, bağlama noktası, dosya sistemi türü, seçenekler, dump bayrağı ve fsck sırası. Seçenekler alanı günlük pratikte en çok önem taşıyandır: defaults, tipik varsayılanların (rw, suid, dev, exec, auto, nouser, async) kısayoludur, noatime her okuma işleminde erişim zaman damgasını güncellememesini sağlar (yoğun kullanılan dosya sistemlerinde gerçek bir G/Ç tasarrufudur, çünkü aksi halde her read() gizlice bir yazma işlemi tetikler) ve ro salt okunur bağlar. mount -a komutu, /etc/fstab'daki henüz bağlanmamış tüm girdileri bağlar — bu, bir düzenlemeyi yeniden başlatmadan test etmenin standart yoludur.

DEEin Dateisystem manuell mit mount /dev/sdb1 /daten zu mounten, gilt nur für diese Sitzung — der Mount ist nach einem Neustart verschwunden. Persistente Mounts werden in /etc/fstab definiert, wo jede Zeile sechs Felder hat: Geräte-Identifikator, Mount-Point, Dateisystemtyp, Optionen, Dump-Flag und fsck-Reihenfolge. Das Optionsfeld ist in der täglichen Praxis am wichtigsten: defaults ist die Kurzform der typischen Defaults (rw, suid, dev, exec, auto, nouser, async), noatime überspringt die Aktualisierung des Zugriffszeitstempels bei jedem Lesen (eine echte I/O-Ersparnis auf stark genutzten Dateisystemen, da sonst jedes read() heimlich ein Schreiben auslöst), und ro mountet schreibgeschützt. mount -a mountet alle noch nicht gemounteten Einträge aus /etc/fstab — der Standardweg, eine Änderung ohne Neustart zu testen.

💡 Tip: noatime is one of the cheapest performance wins available — on a busy read-heavy filesystem, every access-time write it prevents is one less journal commit.
💡 İpucu: noatime, mevcut en ucuz performans kazanımlarından biridir — yoğun okunan bir dosya sisteminde önlediği her erişim zamanı yazması, bir eksik günlük (journal) commit'i demektir.
💡 Hinweis: noatime ist einer der günstigsten verfügbaren Leistungsgewinne — auf einem stark lesenden Dateisystem ist jeder verhinderte Zugriffszeit-Schreibvorgang ein Journal-Commit weniger.

mekanizma The Page Cache and Identifying Devices by UUID — Sayfa önbelleği ve aygıtları UUID ile tanımlama— Der Seiten-Cache und Geräteidentifikation über UUID

Linux keeps all data read from or written to disk in the page cache to boost I/O performance — this cache aggressively occupies a large share of available physical memory, on the principle that "free memory is wasted memory". The buff/cache column in free -h shows exactly this — since it can be reclaimed instantly the moment an application actually needs the RAM, it counts as part of "available" memory and shouldn't be a cause for concern. Writes are usually made to the page cache first and marked dirty; the kernel's background writeback threads flush those dirty pages to disk periodically or under memory pressure. The fsync()/fdatasync() system calls let an application confirm data has actually reached the disk — vital for software that must guarantee durability, such as database systems.

TRLinux, disk G/Ç performansını artırmak için okunan/yazılan tüm dosya verilerini sayfa önbelleğinde (page cache) tutar — bu önbellek, kullanılabilir fiziksel belleğin büyük bir kısmını agresif biçimde işgal eder ("boş bellek israftır" ilkesi). free -h çıktısındaki buff/cache sütunu tam olarak bunu gösterir; bu bellek, bir uygulama tarafından gerçekten talep edildiğinde anında geri kazanılabilir olduğu için "kullanılabilir (available)" belleğin bir parçası sayılır ve endişe kaynağı olmamalıdır. Yazma işlemleri genellikle önce sayfa önbelleğine yapılır ve kirli (dirty) olarak işaretlenir; çekirdeğin arka plan yazma iş parçacıkları (writeback), bu kirli sayfaları periyodik olarak ya da bellek baskısı altında diske gerçekten yazar. fsync()/fdatasync() sistem çağrıları, bir uygulamanın verinin gerçekten diske ulaştığından emin olmasını sağlar — veritabanı sistemleri gibi dayanıklılık (durability) garantisi vermesi gereken yazılımlar için hayati önemdedir.

DELinux hält alle von der Platte gelesenen oder darauf geschriebenen Daten im Seiten-Cache (Page Cache), um die I/O-Leistung zu steigern — dieser Cache belegt aggressiv einen großen Teil des verfügbaren physischen Speichers, nach dem Prinzip "freier Speicher ist verschwendeter Speicher". Die Spalte buff/cache in free -h zeigt genau das — da er in dem Moment sofort zurückgewinnbar ist, in dem eine Anwendung den RAM tatsächlich braucht, zählt er als Teil des "verfügbaren" Speichers und sollte kein Grund zur Sorge sein. Schreibvorgänge erfolgen meist zuerst in den Seiten-Cache und werden als dirty (schmutzig) markiert; die Writeback-Hintergrundthreads des Kernels schreiben diese schmutzigen Seiten periodisch oder unter Speicherdruck tatsächlich auf die Platte. Die Systemaufrufe fsync()/fdatasync() lassen eine Anwendung bestätigen, dass Daten die Platte wirklich erreicht haben — lebenswichtig für Software, die Dauerhaftigkeit (Durability) garantieren muss, etwa Datenbanksysteme.

Identifying devices by UUID. Referring to a device by a device-node name like /dev/sdb1 in /etc/fstab is fragile — disk enumeration order (how the BIOS/UEFI discovers devices) can change between reboots, especially when USB devices are plugged/unplugged or a virtual machine's disk controller changes. That's why modern Linux distributions identify devices by UUID (Universally Unique Identifier) — every filesystem gets a unique UUID at creation time, and it stays fixed regardless of the device's physical location. blkid lists the UUIDs, filesystem types, and labels of every block device on the system; tune2fs -l /dev/sdb1 shows similar (and more detailed) information for the ext family. When a UUID needs to change (say, after cloning a disk, to disambiguate conflicting UUIDs), tune2fs -U random /dev/sdb1 does it. An /etc/fstab entry of the form UUID=3f2a... finds the right filesystem no matter what the device name happens to be — a habit that prevents production servers from silently mounting the wrong disk after a hardware change.

TRAygıtları UUID ile tanımlamak. /etc/fstab'da bir aygıtı /dev/sdb1 gibi bir aygıt düğümü adıyla belirtmek kırılgandır — disk sırası (BIOS/UEFI'nin aygıtları algılama sırası) yeniden başlatmalar arasında değişebilir, özellikle USB aygıtlar takılıp çıkarıldığında ya da sanal makinelerde disk denetleyicisi değiştiğinde. Bu yüzden modern Linux dağıtımları aygıtları UUID (Universally Unique Identifier) ile tanımlar — her dosya sistemi oluşturulduğunda benzersiz bir UUID alır ve bu, aygıtın fiziksel konumundan bağımsız olarak sabit kalır. blkid komutu, sistemdeki tüm blok aygıtlarının UUID'lerini, dosya sistemi türlerini ve etiketlerini listeler; tune2fs -l /dev/sdb1 ext ailesi için benzer (ve daha ayrıntılı) bilgiyi sunar. Bir UUID'yi değiştirmek gerektiğinde (örneğin bir diski klonladıktan sonra çakışan UUID'leri ayırt etmek için) tune2fs -U random /dev/sdb1 kullanılır. /etc/fstab'da UUID=3f2a... biçiminde bir girdi, aygıt adı ne olursa olsun doğru dosya sistemini bulur — bu, üretim sunucularında disk değişimlerinin sessizce yanlış bağlanmaya yol açmasını önleyen kritik bir alışkanlıktır.

DEGeräte über UUID identifizieren. Ein Gerät in /etc/fstab über einen Geräteknotennamen wie /dev/sdb1 anzusprechen, ist fragil — die Reihenfolge der Datenträgererkennung (wie BIOS/UEFI Geräte findet) kann sich zwischen Neustarts ändern, besonders wenn USB-Geräte an-/abgesteckt werden oder sich bei einer virtuellen Maschine der Disk-Controller ändert. Deshalb identifizieren moderne Linux-Distributionen Geräte über die UUID (Universally Unique Identifier) — jedes Dateisystem erhält bei der Erstellung eine eindeutige UUID, die unabhängig von der physischen Position des Geräts fest bleibt. blkid listet die UUIDs, Dateisystemtypen und Labels aller Blockgeräte im System; tune2fs -l /dev/sdb1 zeigt ähnliche (detailliertere) Informationen für die ext-Familie. Muss eine UUID geändert werden (etwa nach dem Klonen einer Platte, um kollidierende UUIDs zu unterscheiden), erledigt das tune2fs -U random /dev/sdb1. Ein /etc/fstab-Eintrag der Form UUID=3f2a... findet das richtige Dateisystem unabhängig vom Gerätenamen — eine Gewohnheit, die verhindert, dass Produktionsserver nach einem Hardwarewechsel still die falsche Platte mounten.

💡 Tip: a growing buff/cache number in free -h is not a leak — it only becomes a problem if available memory stays low even under real application pressure.
💡 İpucu: free -h'deki büyüyen buff/cache sayısı bir sızıntı değildir — sorun ancak gerçek uygulama baskısı altında bile available bellek düşük kalırsa başlar.
💡 Hinweis: eine wachsende buff/cache-Zahl in free -h ist kein Leck — ein Problem wird es erst, wenn available auch unter echtem Anwendungsdruck niedrig bleibt.

mekanizma The Mount Mechanism, the Namespace Tree, and /proc & /sys — Bağlama mekanizması, ad alanı ağacı ve /proc & /sys— Der Mount-Mechanismus, der Namespace-Baum und /proc & /sys

The mount() system call attaches the root of a filesystem onto a specific point ("mount point") in the existing directory tree. Linux has a single, unified directory tree rooted at / — unlike Windows, there are no separate drive letters; every additional storage device, network filesystem (NFS, SMB), or special virtual filesystem (/proc, /sys) gets "attached" at some point in that one tree. Mount namespaces, which we'll meet properly in Ch. 18, build directly on this: they let different process groups see different views of the directory tree, one of the foundational building blocks of container isolation.

TRmount() sistem çağrısı, bir dosya sisteminin kök dizinini, mevcut dizin ağacının belirli bir noktasına ("mount point") ekler. Linux'ta tek bir birleşik dizin ağacı (/'tan başlayan) vardır — Windows'un aksine ayrı sürücü harfleri yoktur; her ek depolama aygıtı, ağ üzerinden erişilen bir dosya sistemi (NFS, SMB) ya da özel bir sanal dosya sistemi (/proc, /sys) bu tek ağacın bir noktasına "iliştirilir". Bölüm 18'de tam olarak göreceğimiz mount ad alanları (namespace), doğrudan bunun üzerine kurulur: farklı süreç gruplarına dizin ağacının farklı görünümlerini sunarak konteyner izolasyonunun temel taşlarından birini oluşturur.

DEDer Systemaufruf mount() hängt die Wurzel eines Dateisystems an einen bestimmten Punkt ("Mount-Point") im bestehenden Verzeichnisbaum. Linux hat einen einzigen, vereinheitlichten Verzeichnisbaum mit Wurzel / — anders als bei Windows gibt es keine separaten Laufwerksbuchstaben; jedes zusätzliche Speichergerät, jedes Netzwerk-Dateisystem (NFS, SMB) oder spezielle virtuelle Dateisystem (/proc, /sys) wird an irgendeinem Punkt dieses einen Baums "angehängt". Mount-Namespaces, denen wir in Kapitel 18 richtig begegnen, bauen direkt darauf auf: sie lassen verschiedene Prozessgruppen unterschiedliche Ansichten des Verzeichnisbaums sehen — einer der Grundbausteine der Container-Isolation.

/proc and /sys are virtual filesystems: not real files on disk, but kernel state presented, at runtime, "as if" it were files. Under /proc/<pid>/ every process's state is readable, /proc/meminfo exposes system memory statistics, and /sys/class/ exposes device and driver information — both readable and, in many cases, writable. This gives the kernel and user space a communication channel that is far more discoverable and scriptable than ioctl() — plenty of system administration tools (systemd, monitoring agents) work by reading these files directly rather than calling any dedicated API.

TR/proc ve /sys, disk üzerinde gerçek dosyalar değil, çekirdek durumunun çalışma zamanında "dosya" biçiminde sunulduğu sanal dosya sistemleridir. /proc/<pid>/ altında her sürecin durumu, /proc/meminfo altında sistem bellek istatistikleri, /sys/class/ altında aygıt ve sürücü bilgileri okunabilir — hatta çoğu durumda yazılabilir. Bu, çekirdek ile kullanıcı alanı arasında ioctl()'e göre çok daha keşfedilebilir, script'lenebilir bir iletişim kanalı sağlar — pek çok sistem yönetim aracı (systemd, izleme araçları) özel bir API çağırmak yerine doğrudan bu dosyaları okuyarak çalışır.

DE/proc und /sys sind virtuelle Dateisysteme: keine echten Dateien auf der Platte, sondern Kernel-Zustand, der zur Laufzeit "als ob" er Dateien wären präsentiert wird. Unter /proc/<pid>/ ist der Zustand jedes Prozesses lesbar, /proc/meminfo zeigt Systemspeicherstatistiken, und /sys/class/ zeigt Geräte- und Treiberinformationen — beides lesbar und in vielen Fällen auch schreibbar. Das gibt Kernel und Userspace einen Kommunikationskanal, der weit entdeckbarer und skriptfähiger ist als ioctl() — zahlreiche Systemverwaltungswerkzeuge (systemd, Monitoring-Agenten) funktionieren, indem sie diese Dateien direkt lesen, statt eine dedizierte API aufzurufen.

💡 Tip: when you're unsure whether some kernel behavior is tunable, check /proc/sys/ and /sys/ first — a huge share of runtime kernel configuration lives there as plain readable/writable files.
💡 İpucu: bir çekirdek davranışının ayarlanabilir olup olmadığından emin değilsen önce /proc/sys/ ve /sys/'e bak — çalışma zamanı çekirdek ayarlarının büyük kısmı orada sıradan okunabilir/yazılabilir dosyalar olarak yaşar.
💡 Hinweis: bist du unsicher, ob ein Kernel-Verhalten einstellbar ist, prüfe zuerst /proc/sys/ und /sys/ — ein Großteil der Laufzeit-Kernelkonfiguration lebt dort als gewöhnliche lesbare/schreibbare Dateien.

derinlemesine statx() and Journaling / Data Integrity — statx() ve günlükleme / veri bütünlüğü— statx() und Journaling/Datenintegrität

The classic stat() system call historically returned a fixed structure that wasn't extensible enough across differing filesystems. Modern Linux offers statx(), which lets a caller specify exactly which fields it actually wants (skipping unneeded ones for performance) and can carry extra information some modern filesystems provide — creation time (never tracked by many older filesystems at all), or a filesystem's block size. This is a clean example of how VFS (§7.1) evolves over time, replacing the rigidity of an older interface with a modern, flexible one without breaking anything that still relies on the old one.

TRKlasik stat() sistem çağrısı, tarihsel olarak dosya sistemleri arasında yeterince genişletilebilir olmayan sabit bir yapı döndürürdü. Modern Linux, çağıranın gerçekten hangi alanları istediğini belirtmesine (performans için gereksiz alanları atlayarak) izin veren ve bazı modern dosya sistemlerinin sunduğu ek bilgileri (birçok eski dosya sisteminde hiç tutulmayan oluşturulma zamanı ya da dosya sisteminin blok boyutu gibi) taşıyabilen statx() sistem çağrısını sunar. Bu, VFS'nin (§7.1) zaman içinde nasıl evrildiğinin, eski arayüzlerin katılığının modern, esnek bir arayüzle nasıl aşıldığının — eskiye hâlâ dayananı bozmadan — güzel bir örneğidir.

DEDer klassische Systemaufruf stat() lieferte historisch eine feste Struktur, die über verschiedene Dateisysteme hinweg nicht erweiterbar genug war. Modernes Linux bietet statx(), mit dem ein Aufrufer genau angeben kann, welche Felder er tatsächlich möchte (unnötige Felder aus Performancegründen überspringen), und das zusätzliche Informationen tragen kann, die manche moderne Dateisysteme bieten — Erstellungszeit (bei vielen älteren Dateisystemen nie erfasst) oder die Blockgröße eines Dateisystems. §7.3 mentioned ext4's journaling feature; understanding why it exists illuminates a fundamental problem in filesystem design. A filesystem update (say, creating a file) usually requires several disk writes: allocate a new inode, update the directory entry, mark the data blocks. If the system crashes or loses power in the middle of that multi-write sequence, the filesystem can be left inconsistent — a directory entry might exist while its corresponding inode was never written. Journaling solves this: before touching the real data structures, a record of the intended changes is written to a special, separate area (the journal/log) and marked "complete" with a commit marker. Only after that commit are the real data structures updated. If the system crashes during that real update, the filesystem reads the journal on next boot and either finishes or fully rolls back the half-done operation — it never stays in a partial, inconsistent state. Conceptually, this is identical to the write-ahead logging (WAL) technique used by database systems — a useful connection point for seeing the same core idea recur at different layers (filesystem and database).

TR§7.3'te ext4'ün günlükleme özelliğinden bahsetmiştik; bu mekanizmanın neden var olduğunu derinlemesine anlamak, dosya sistemi tasarımının temel bir sorununu aydınlatır. Bir dosya sistemi güncellemesi (örneğin bir dosya oluşturmak) genellikle birden fazla disk yazma işlemi gerektirir: yeni bir inode ayır, dizin girdisini güncelle, veri bloklarını işaretle. Eğer sistem bu çoklu yazma işleminin ortasında çöker/elektrik kesilirse, dosya sistemi tutarsız bir durumda kalabilir — örneğin bir dizin girdisi var ama karşılık gelen inode henüz yazılmamış. Günlükleme, bu sorunu şöyle çözer: gerçek veri yapılarını değiştirmeden önce, yapılacak değişikliklerin bir kaydı (journal/log) özel, ayrı bir alana yazılır ve bu yazmanın "tamamlandığı" bir işaretle onaylanır (commit). Ancak bu onaydan sonra gerçek veri yapıları güncellenir. Eğer sistem gerçek güncelleme sırasında çökerse, bir sonraki açılışta dosya sistemi günlüğü okur ve yarım kalan işlemleri ya tamamlar ya da tamamen geri alır (rollback) — kısmi, tutarsız bir durumda asla kalınmaz. Bu, veritabanı sistemlerindeki WAL (Write-Ahead Logging) tekniğiyle kavramsal olarak birebir aynıdır — aynı temel fikrin farklı katmanlarda (dosya sistemi ve veritabanı) nasıl tekrar tekrar ortaya çıktığını görmek için değerli bir bağlantı noktasıdır.

DE§7.3 erwähnte ext4s Journaling-Funktion; zu verstehen, warum sie existiert, beleuchtet ein grundlegendes Problem im Dateisystem-Design. Eine Dateisystem-Aktualisierung (z. B. das Erstellen einer Datei) erfordert meist mehrere Schreibvorgänge: einen neuen Inode zuweisen, den Verzeichniseintrag aktualisieren, Datenblöcke markieren. Stürzt das System mitten in dieser Mehrfach-Schreibsequenz ab oder fällt der Strom aus, kann das Dateisystem inkonsistent bleiben — etwa ein Verzeichniseintrag existiert, während der zugehörige Inode nie geschrieben wurde. Journaling löst das: bevor die echten Datenstrukturen berührt werden, wird ein Protokoll der beabsichtigten Änderungen in einen speziellen, separaten Bereich (das Journal/Log) geschrieben und mit einer Commit-Markierung als "abgeschlossen" markiert. Erst nach diesem Commit werden die echten Datenstrukturen aktualisiert. Stürzt das System während dieser echten Aktualisierung ab, liest das Dateisystem beim nächsten Boot das Journal und beendet oder verwirft die halbfertige Operation vollständig (Rollback) — es bleibt nie in einem teilweisen, inkonsistenten Zustand. Konzeptionell ist das identisch mit der Write-Ahead-Logging (WAL)-Technik von Datenbanksystemen — ein wertvoller Anknüpfungspunkt, um dieselbe Grundidee auf verschiedenen Schichten (Dateisystem und Datenbank) wiederkehren zu sehen.

Btrfs takes a different approach: copy-on-write (a conceptual relative of fork()'s COW from §5.3) — when a block is about to change, the old block is never modified in place; a new copy is written instead, and higher-level pointers (the metadata tree) are atomically updated to point at the new block. This gives a different consistency guarantee than journaling and naturally supports snapshots: keeping an old "root" pointer around gives a snapshot of the entire filesystem state at that moment essentially for free — through shared blocks, with no extra copying.

TRBtrfs ise farklı bir yaklaşım kullanır: copy-on-write (§5.3'teki fork() COW'unun kavramsal akrabası) — bir blok değiştirilmek istendiğinde, eski blok yerinde değiştirilmez, yeni bir kopyaya yazılır ve üst düzey işaretçiler (metadata ağacı) yeni bloğu göstermek üzere atomik olarak güncellenir. Bu yaklaşım, günlüklemeye kıyasla farklı bir tutarlılık garantisi sunar ve doğal olarak anlık görüntü (snapshot) özelliğini destekler — eski bir "kök" işaretçisini saklamak, o andaki tüm dosya sistemi durumunun bir anlık görüntüsünü bedavaya (ekstra kopyalama olmadan, sadece paylaşılan bloklar üzerinden) sağlar.

DEBtrfs verfolgt einen anderen Ansatz: Copy-on-Write (ein konzeptioneller Verwandter des fork()-COW aus §5.3) — soll ein Block geändert werden, wird der alte Block nie an Ort und Stelle verändert; stattdessen wird eine neue Kopie geschrieben, und übergeordnete Zeiger (der Metadaten-Baum) werden atomar aktualisiert, um auf den neuen Block zu zeigen. Das bietet eine andere Konsistenzgarantie als Journaling und unterstützt naturgemäß Snapshots: einen alten "Wurzel"-Zeiger aufzubewahren liefert praktisch kostenlos einen Schnappschuss des gesamten Dateisystemzustands zu diesem Zeitpunkt — über geteilte Blöcke, ohne zusätzliches Kopieren.

💡 Tip: journaling and COW answer the same question ("how do we survive a crash mid-write?") with two different mechanisms — recognizing that pattern makes both easier to remember.
💡 İpucu: günlükleme ve COW, aynı soruyu ("yazma ortasında çökmeyi nasıl atlatırız?") iki farklı mekanizmayla yanıtlar — bu deseni fark etmek her ikisini de hatırlamayı kolaylaştırır.
💡 Hinweis: Journaling und COW beantworten dieselbe Frage ("wie überstehen wir einen Absturz mitten im Schreiben?") mit zwei verschiedenen Mechanismen — dieses Muster zu erkennen erleichtert, sich beide zu merken.

VFS's abstraction power (§7.1-7.2) extends to filesystems accessed over the network (NFS, CIFS/SMB) as much as to local ones — an application calling open()/read()/write() doesn't need to know whether the target is a local disk or a remote server. But that transparency carries hidden complexity costs: the consistency model differs from local filesystems. NFS's traditional close-to-open consistency model means one client's changes are only guaranteed visible to other clients once the file is closed (and reopened) — a marked difference from the near-instant consistency of a local filesystem on the same machine, and a reminder that applications relying on files shared across a distributed system need careful design. This connects back to the IPC discussion in Ch. 11: in some scenarios, an explicitly designed messaging protocol (socket-based) offers a far more predictable consistency guarantee than a file shared over the network.

TRVFS'nin (§7.1-7.2) soyutlama gücü, yerel dosya sistemleri kadar ağ üzerinden erişilen dosya sistemlerini de (NFS, CIFS/SMB) aynı arayüz altında sunabilmesinde görülür — bir uygulama open()/read()/write() çağırdığında, hedefin yerel bir disk mi yoksa ağ üzerindeki bir sunucu mu olduğunu bilmek zorunda değildir. Ama bu şeffaflık, gizli karmaşıklık bedelleri getirir: tutarlılık modeli yerel dosya sistemlerinden farklıdır. NFS'in geleneksel kapatma-üzerine-yaz (close-to-open) tutarlılık modeli, bir istemcinin yaptığı değişikliklerin diğer istemcilere ancak dosya kapatıldığında (ve yeniden açıldığında) garanti edilen biçimde görünür olacağı anlamına gelir — bu, yerel dosya sistemlerinin (aynı makinede) neredeyse anlık tutarlılığından belirgin biçimde farklıdır ve dağıtık sistemlerde paylaşılan dosyalara güvenen uygulamaların dikkatle tasarlanması gerektiğini gösterir. Bu, Bölüm 11'deki IPC tartışmasıyla da bağlantılıdır: bazı senaryolarda, ağ üzerinden paylaşılan bir dosya yerine, açıkça tasarlanmış bir mesajlaşma protokolü (soket tabanlı) çok daha öngörülebilir bir tutarlılık garantisi sunar.

DEDie Abstraktionskraft von VFS (§7.1-7.2) zeigt sich darin, dass es über das Netzwerk erreichbare Dateisysteme (NFS, CIFS/SMB) genauso unter derselben Schnittstelle anbieten kann wie lokale — eine Anwendung, die open()/read()/write() aufruft, muss nicht wissen, ob das Ziel eine lokale Platte oder ein entfernter Server ist. Doch diese Transparenz bringt versteckte Komplexitätskosten mit sich: das Konsistenzmodell unterscheidet sich von lokalen Dateisystemen. NFS' traditionelles Close-to-Open-Konsistenzmodell bedeutet, dass die Änderungen eines Clients anderen Clients erst garantiert sichtbar sind, wenn die Datei geschlossen (und wieder geöffnet) wurde — ein deutlicher Unterschied zur nahezu sofortigen Konsistenz eines lokalen Dateisystems auf derselben Maschine, und eine Erinnerung, dass Anwendungen, die sich auf über ein verteiltes System geteilte Dateien verlassen, sorgfältig entworfen werden müssen. Das knüpft an die IPC-Diskussion in Kapitel 11 an: in manchen Szenarien bietet ein explizit entworfenes Nachrichtenprotokoll (Socket-basiert) eine weit vorhersagbarere Konsistenzgarantie als eine über das Netzwerk geteilte Datei.

A filesystem's lifecycle meets three core maintenance tools. mkfs (make filesystem) builds a fresh filesystem structure (superblock, inode tables, root directory) on an empty block device — invoked as mkfs.ext4 /dev/sdb1 or mkfs -t xfs /dev/sdb1; each filesystem type has its own mkfs.<type> program, and mkfs itself is really a thin wrapper around them. fsck (file system check) scans a filesystem tree for inconsistencies — orphaned inodes, bad link counts, corrupted directory entries — and repairs them, typically with the -y flag to auto-confirm; thanks to journaling (§7.9), fsck is rarely needed on modern ext4/XFS, but it remains indispensable in edge cases like hardware faults or a corrupted journal itself. tune2fs adjusts an already-existing ext-family filesystem while it's unmounted — changing its label, adjusting the automatic fsck interval, or adding/removing journaling after the fact.

TRBir dosya sistemi yaşam döngüsü boyunca üç temel bakım aracıyla karşılaşılır. mkfs (make filesystem), boş bir blok aygıtı üzerine yeni bir dosya sistemi yapısı (superblock, inode tabloları, kök dizin) kurar — mkfs.ext4 /dev/sdb1 ya da mkfs -t xfs /dev/sdb1 gibi biçimlerde çağrılır; her dosya sistemi türü için ayrı bir mkfs.<tür> programı vardır, mkfs komutu aslında bunlar için ince bir sarmalayıcı (wrapper) işlevi görür. fsck (file system check), bir dosya sistemi ağacını tarayarak tutarsızlıkları (yetim inode'lar, hatalı bağlantı sayıları, bozuk dizin girdileri) tespit eder ve — genellikle -y bayrağıyla otomatik onay vererek — onarır; günlükleme (§7.9) sayesinde modern ext4/XFS sistemlerinde fsck'a ihtiyaç nadirdir, ama donanım hatası ya da günlüğün kendisinin bozulması gibi uç durumlarda hâlâ vazgeçilmezdir. tune2fs, zaten var olan bir ext ailesi dosya sistemini bağlamadan (unmount edilmiş haldeyken) ayarlamaya yarar — etiket değiştirme, otomatik fsck aralığını ayarlama, günlükleme özelliğini sonradan ekleme/kaldırma gibi işlemler buradan yapılır.

DEDer Lebenszyklus eines Dateisystems begegnet drei zentralen Wartungswerkzeugen. mkfs (make filesystem) baut auf einem leeren Blockgerät eine neue Dateisystemstruktur (Superblock, Inode-Tabellen, Wurzelverzeichnis) auf — aufgerufen als mkfs.ext4 /dev/sdb1 oder mkfs -t xfs /dev/sdb1; jeder Dateisystemtyp hat sein eigenes Programm mkfs.<typ>, und mkfs selbst ist eigentlich nur ein dünner Wrapper darum. fsck (file system check) scannt einen Dateisystembaum nach Inkonsistenzen — verwaiste Inodes, falsche Link-Zähler, beschädigte Verzeichniseinträge — und repariert sie, typischerweise mit dem Flag -y zur automatischen Bestätigung; dank Journaling (§7.9) ist fsck auf modernem ext4/XFS selten nötig, bleibt aber in Grenzfällen wie Hardwarefehlern oder einem beschädigten Journal selbst unverzichtbar. tune2fs passt ein bereits bestehendes Dateisystem der ext-Familie an, während es ungemountet ist — Label ändern, das automatische fsck-Intervall anpassen oder Journaling nachträglich hinzufügen/entfernen.

The inode-exhaustion mystery: "there's disk space, but I can't create a file". When a filesystem is created, the size of its inode table is fixed up front — calculated by dividing disk capacity by an estimated average file size. If a system accumulates far more small files than expected (thousands of tiny cache files, or messages piling up in a maildir-format mail queue), the inode table can run out even while free bytes remain on disk — and new file-creation attempts fail with "No space left on device", exactly as if the disk were truly full. Unlike df -h, the df -i command reports inode counts, not bytes; if the IUse% column is approaching 100%, the problem is inode exhaustion, not disk space. The fix is either cleaning up unnecessary small files or, where possible, recreating the filesystem with a higher inode ratio — a concrete, operational reminder that the inode object we met in §7.2 is a real, finite resource.

TRinode tükenmesi: "diskte yer var ama dosya oluşturulamıyor" bilmecesi. Bir dosya sistemi oluşturulduğunda, inode tablosunun boyutu önceden sabitlenir — disk kapasitesinin tahmini ortalama dosya boyutuna göre bölünmesiyle hesaplanır. Eğer bir sistemde beklenenin çok üzerinde sayıda küçük dosya birikirse (örneğin binlerce küçük önbellek dosyası, e-posta kuyruğunda maildir formatında biriken mesajlar), disk üzerinde hâlâ boş byte olsa bile inode tablosu tükenebilir — ve yeni dosya oluşturma girişimleri "No space left on device" hatasıyla başarısız olur, tıpkı disk gerçekten doluymuş gibi. df -i komutu, df -h'nin aksine byte değil inode sayısını raporlar; IUse% sütunu %100'e yaklaşıyorsa, sorun disk alanı değil inode tükenmesidir. Çözüm ya gereksiz küçük dosyaları temizlemek ya da (mümkünse) dosya sistemini daha büyük bir inode oranıyla yeniden oluşturmaktır — inode sayısı, §7.2'de tanıştığımız inode nesnesinin somut, sınırlı bir kaynak olduğunun operasyonel bir hatırlatıcısıdır.

DEDas Rätsel der Inode-Erschöpfung: "es gibt Plattenplatz, aber ich kann keine Datei erstellen". Wird ein Dateisystem erstellt, wird die Größe seiner Inode-Tabelle vorab festgelegt — berechnet, indem die Plattenkapazität durch eine geschätzte durchschnittliche Dateigröße geteilt wird. Sammelt ein System weit mehr kleine Dateien an als erwartet (Tausende winziger Cache-Dateien oder sich stapelnde Nachrichten in einer Mail-Warteschlange im Maildir-Format), kann die Inode-Tabelle erschöpft sein, obwohl noch freie Bytes auf der Platte vorhanden sind — und neue Dateierstellungsversuche schlagen mit "No space left on device" fehl, genau als wäre die Platte wirklich voll. Anders als df -h meldet df -i Inode-Zahlen, keine Bytes; nähert sich die Spalte IUse% 100%, liegt das Problem an Inode-Erschöpfung, nicht am Plattenplatz. Die Lösung ist entweder das Aufräumen unnötiger kleiner Dateien oder, wo möglich, das Neuerstellen des Dateisystems mit einem höheren Inode-Verhältnis — eine konkrete, operative Erinnerung daran, dass das Inode-Objekt aus §7.2 eine echte, endliche Ressource ist.

💡 Tip: keep this diagnostic pair in mind: df -h tells you about bytes, df -i tells you about inodes — a "disk full" symptom with plenty of free bytes almost always means it's time to check the second one.
