temel kavram Why the Kernel Has Its Own Data-Structure Library — Neden çekirdeğin kendi veri yapısı kütüphanesi var?— Warum der Kernel eine eigene Datenstruktur-Bibliothek hat

User-space programmers usually reach for ready-made, general-purpose collection libraries — C++'s STL, Python's built-in lists/dicts/sets. The kernel has none of these luxuries: it is written in plain C (no generic templates), memory allocation is constrained (§6), and performance matters at every layer. So the Linux kernel has grown its own small set of extremely optimized, reusable core data-structure implementations — understanding them is a prerequisite for reading kernel source code at all.

TRKullanıcı alanı programcıları genellikle C++'ın STL'i, Python'un yerleşik koleksiyonları gibi hazır, genel amaçlı veri yapısı kütüphanelerine güvenir. Çekirdek bu lükse sahip değildir: C dilinde yazılır (jenerik şablonlar yoktur), bellek ayırma kısıtlıdır (Bölüm 6), performans her düzeyde kritik önemdedir. Bu yüzden Linux çekirdeği, kendi son derece optimize edilmiş, tekrar kullanılabilir temel veri yapısı implementasyonlarını geliştirmiştir — bunları anlamak, çekirdek kaynak kodunu okuyabilmenin ön koşuludur.

DEUserspace-Programmierer greifen üblicherweise zu fertigen, universellen Collection-Bibliotheken — der STL von C++, den eingebauten Listen/Dicts/Sets von Python. Der Kernel hat diesen Luxus nicht: er ist in reinem C geschrieben (keine generischen Templates), die Speicherzuteilung ist eingeschränkt (§6), und Performance zählt auf jeder Ebene. Deshalb hat der Linux-Kernel seine eigene kleine Sammlung extrem optimierter, wiederverwendbarer Kern-Datenstrukturen entwickelt — sie zu verstehen ist eine Voraussetzung, um überhaupt Kernel-Quellcode lesen zu können.

💡 Tip: none of the structures in this chapter come from an STL-like generic library — they are all written by hand in C, with macros doing the work generics would do elsewhere; expect to see the same patterns (especially container_of(), introduced in §17.2) recur again and again across unrelated subsystems.
💡 İpucu: bu bölümdeki veri yapılarının hiçbiri STL benzeri jenerik bir kütüphaneden gelmez — hepsi C dilinde, jeneriklerin başka dillerde yaptığı işi makrolarla yaparak elle yazılmıştır; aynı desenlerin (özellikle Bölüm 17.2'de tanıtılan container_of()) birbiriyle ilgisiz alt sistemlerde defalarca tekrarlandığını göreceksin.
💡 Hinweis: keine der Strukturen in diesem Kapitel stammt aus einer STL-ähnlichen generischen Bibliothek — sie sind alle von Hand in C geschrieben, wobei Makros die Arbeit übernehmen, die anderswo Generics erledigen würden; erwarte, dass dieselben Muster (insbesondere container_of(), eingeführt in §17.2) in völlig unabhängigen Subsystemen immer wieder auftauchen.

mekanizma The Doubly-Linked Circular List: struct list_head — Çift yönlü dairesel bağlı liste: struct list_head— Die doppelt verkettete zirkuläre Liste: struct list_head

The kernel's most widely used data structure is struct list_head, defined in <linux/list.h>. Its design is conceptually different from a traditional linked list: a normal list node contains the data (struct node { int data; struct node *next; }); Linux's list_head takes the opposite approach — the data structure itself embeds a list_head field, and the list only links those embedded fields together. This is known as an "intrusive list" pattern.

TRÇekirdeğin en yaygın kullanılan veri yapısı, <linux/list.h> içinde tanımlanan struct list_head'dir. Bu yapının tasarımı, geleneksel bağlı liste implementasyonlarından kavramsal olarak farklıdır: normal bir bağlı listede düğüm, veriyi içerir (struct node { int data; struct node *next; }); Linux'un list_head'i ise tam tersi bir yaklaşım kullanır — veri yapısının kendisi bir list_head alanı içerir, ve liste sadece bu list_head alanlarını birbirine bağlar. Bu, "intrusive list" (müdahaleci liste) deseni olarak bilinir.

DEDie am häufigsten verwendete Datenstruktur des Kernels ist struct list_head, definiert in <linux/list.h>. Ihr Design unterscheidet sich konzeptionell von einer traditionellen verketteten Liste: ein normaler Listenknoten enthält die Daten (struct node { int data; struct node *next; }); Linux' list_head verfolgt den umgekehrten Ansatz — die Datenstruktur selbst enthält ein list_head-Feld, und die Liste verknüpft nur diese eingebetteten Felder miteinander. Dies ist als "intrusive list"-Muster (müdahaleci Liste) bekannt.

The practical benefit is large: the same list_head implementation can link completely different kinds of data structures (a task_struct, an inode, a device structure) without any generic-programming (template/generics) mechanism. Getting back from a list_head pointer to the real data structure requires the container_of() macro — this macro reverses, at compile time, a struct member's address back to the start address of the struct that contains it, using a compile-time-computed offset. container_of() is one of the most frequently encountered macros in kernel source code, and although confusing at first sight, it is the C-language answer to "type-safe generic programming" in kernel style. The list is both doubly linked (every node carries both a next and a prev pointer) and circular (the last node's next points to the head, the first node's prev points to the tail) — this simplifies inserting/removing a node from any position in O(1) time, without special-casing the list's head or tail.

TRBunun pratik faydası büyüktür: aynı list_head implementasyonu, tamamen farklı türdeki veri yapılarını (bir task_struct, bir inode, bir aygıt yapısı) hiçbir jenerik programlama (template/generic) mekanizmasına ihtiyaç duymadan bağlayabilir. Bir list_head işaretçisinden gerçek veri yapısına geri dönmek için container_of() makrosu kullanılır — bu makro, bir yapı üyesinin adresinden, o üyeyi içeren yapının başlangıç adresini, derleme zamanında hesaplanan ofset bilgisiyle geri hesaplar. container_of(), çekirdek kaynak kodunda en sık karşılaşılan makrolardan biridir ve ilk kez görüldüğünde kafa karıştırıcı olsa da, çekirdek stilinde "tip güvenli jenerik programlamanın" C dilindeki temel çözümüdür. Liste, çift yönlü (her düğüm hem next hem prev işaretçisi taşır) ve dairesel (son düğümün next'i başa, ilk düğümün prev'i sona işaret eder) olarak tasarlanmıştır — bu, bir düğümü listenin herhangi bir yerinden O(1) sürede ekleme/çıkarma işlemini, listenin başını/sonunu özel olarak ele almaya gerek kalmadan basitleştirir.

DEDer praktische Nutzen ist groß: dieselbe list_head-Implementierung kann völlig unterschiedliche Arten von Datenstrukturen (eine task_struct, eine Inode, eine Gerätestruktur) verknüpfen, ohne jeden Generics-Mechanismus (Templates/generische Programmierung). Um von einem list_head-Zeiger zur echten Datenstruktur zurückzukommen, wird das Makro container_of() verwendet — es berechnet, ausgehend von der Adresse eines Strukturmitglieds, mithilfe eines zur Kompilierzeit berechneten Offsets die Startadresse der es enthaltenden Struktur zurück. container_of() ist eines der am häufigsten anzutreffenden Makros im Kernel-Quellcode und ist, obwohl beim ersten Anblick verwirrend, die C-Antwort auf "typsichere generische Programmierung" im Kernel-Stil. Die Liste ist sowohl doppelt verkettet (jeder Knoten trägt sowohl einen next- als auch einen prev-Zeiger) als auch zirkulär (das next des letzten Knotens zeigt auf den Kopf, das prev des ersten Knotens auf das Ende) — das vereinfacht das Einfügen/Entfernen eines Knotens an beliebiger Stelle in O(1)-Zeit, ohne Kopf oder Ende der Liste als Sonderfall behandeln zu müssen.

💡 Tip: don't blindly port a userspace linked-list tutorial's mental model here — in an intrusive list, the "node" you're linking IS the data structure (or rather, a field inside it), not a separate wrapper object that points at the data.
💡 İpucu: buraya kullanıcı alanı bağlı liste eğitimlerinin zihinsel modelini körü körüne taşıma — müdahaleci bir listede bağladığın "düğüm", veriyi işaret eden ayrı bir sarmalayıcı nesne değil, veri yapısının kendisidir (daha doğrusu, içindeki bir alandır).
💡 Hinweis: übertrage hier nicht blind das mentale Modell eines Userspace-Tutorials zu verketteten Listen — in einer intrusive list ist der "Knoten", den du verknüpfst, die Datenstruktur selbst (genauer: ein Feld darin), kein separates Wrapper-Objekt, das auf die Daten zeigt.

performans Red-Black Trees — Kırmızı-siyah ağaçlar— Rot-Schwarz-Bäume

§3 showed that the CFS scheduler orders runnable tasks by vruntime using a red-black tree. A red-black tree is a self-balancing binary search tree — every node is colored "red" or "black", and specific coloring rules guarantee that the longest branch is never more than twice as long as the shortest one. This balance guarantee ensures search, insert, and delete always complete in O(log n) time — a critical safeguard against an unbalanced tree degenerating, in the worst case, into O(n) (a linked list).

TRBölüm 3'te CFS zamanlayıcısının süreçleri vruntime'a göre sıraladığını, bunun için bir kırmızı-siyah ağaç kullandığını görmüştük. Kırmızı-siyah ağaç, kendi kendini dengeleyen bir ikili arama ağacıdır — her düğüm "kırmızı" ya da "siyah" renklendirilir, ve belirli renklendirme kurallarına uyularak, ağacın en uzun dalının en kısa dalından asla iki kattan fazla uzun olmaması garanti edilir. Bu denge garantisi, arama, ekleme ve silme işlemlerinin her zaman O(log n) sürede tamamlanmasını sağlar — bu, dengesiz bir ağacın en kötü durumda O(n)'e (bağlı listeye) dejenere olma riskine karşı kritik bir garantidir.

DE§3 zeigte, dass der CFS-Scheduler lauffähige Tasks anhand von vruntime mit einem Rot-Schwarz-Baum ordnet. Ein Rot-Schwarz-Baum ist ein sich selbst balancierender binärer Suchbaum — jeder Knoten wird "rot" oder "schwarz" gefärbt, und bestimmte Färbungsregeln garantieren, dass der längste Zweig nie mehr als doppelt so lang ist wie der kürzeste. Diese Balance-Garantie stellt sicher, dass Suchen, Einfügen und Löschen stets in O(log n)-Zeit abgeschlossen sind — eine kritische Absicherung gegen einen unbalancierten Baum, der im schlimmsten Fall zu O(n) (einer verketteten Liste) entartet.

CFS's choice of a red-black tree is not accidental: the scheduler constantly, at high frequency, performs "find the task with the smallest vruntime" (the leftmost node — O(log n), often O(1) via a cached pointer) and "update a task's position in the tree when its vruntime changes" (delete + re-insert — O(log n)). The red-black tree's guaranteed logarithmic performance keeps scheduling decisions predictably fast even with thousands of tasks. Red-black trees also show up elsewhere in the kernel (memory-region/VMA management, file-system metadata structures) for the same reason.

TRCFS'in kırmızı-siyah ağaç seçimi tesadüfi değildir: zamanlayıcı, "en küçük vruntime'a sahip görevi bul" (en soldaki düğüm — O(log n), genellikle önbelleğe alınmış bir işaretçiyle O(1)) ve "bir görevin vruntime'ı değiştiğinde ağaçtaki konumunu güncelle" (silme + yeniden ekleme — O(log n)) işlemlerini sürekli, yüksek frekansta yapar; kırmızı-siyah ağacın garantili logaritmik performansı, binlerce görev olsa bile zamanlama kararlarının öngörülebilir hızda kalmasını sağlar. Çekirdeğin diğer birçok yerinde de (bellek bölgesi (VMA) yönetimi, dosya sistemi meta veri yapıları) aynı gerekçeyle kırmızı-siyah ağaçlar kullanılır.

DECFS' Wahl eines Rot-Schwarz-Baums ist kein Zufall: der Scheduler führt ständig, mit hoher Frequenz, "finde den Task mit dem kleinsten vruntime" (der am weitesten links liegende Knoten — O(log n), oft O(1) über einen zwischengespeicherten Zeiger) und "aktualisiere die Position eines Tasks im Baum, wenn sich sein vruntime ändert" (Löschen + Neueinfügen — O(log n)) aus; die garantiert logarithmische Leistung des Rot-Schwarz-Baums hält Scheduling-Entscheidungen selbst bei tausenden Tasks vorhersehbar schnell. Rot-Schwarz-Bäume tauchen aus demselben Grund auch an vielen anderen Stellen im Kernel auf (Speicherregion/VMA-Verwaltung, Dateisystem-Metadatenstrukturen).

Another important use of red-black trees is the kernel's epoll subsystem — the mechanism from §11 that efficiently monitors large numbers of file descriptors. When an application calls epoll_ctl(EPOLL_CTL_ADD, fd, ...) to add thousands of sockets to a single epoll instance, the kernel keeps those descriptors — a set needing fast add, remove, and lookup — in a red-black tree. This is a concrete example of how data-structure choice directly translates into system-call performance: if the kernel used a plain linked list instead, each epoll_ctl call's cost would grow linearly (O(n)) with the number of watched descriptors, whereas the red-black tree cuts that to O(log n) — on a server managing tens of thousands of concurrent connections, that difference directly affects how many requests per second it can handle.

TRKırmızı-siyah ağaçların bir diğer önemli kullanım yeri, çekirdeğin epoll alt sistemidir — Bölüm 11'de tartıştığımız, çok sayıda dosya tanıtıcısını verimli biçimde izlemeye yarayan mekanizma. Bir uygulama epoll_ctl(EPOLL_CTL_ADD, fd, ...) çağırarak binlerce soketi tek bir epoll örneğine eklediğinde, çekirdek bu tanıtıcıları — hızlı ekleme, silme ve arama gerektiren bir küme olarak — yine bir kırmızı-siyah ağaçta tutar. Bu, veri yapısı seçiminin sistem çağrısı performansına doğrudan yansıdığı somut bir örnektir: eğer çekirdek bunun yerine basit bir bağlı liste kullansaydı, epoll_ctl çağrılarının maliyeti izlenen tanıtıcı sayısıyla doğrusal artardı (O(n)), oysa kırmızı-siyah ağaç bu maliyeti O(log n)'e indirger — on binlerce eşzamanlı bağlantıyı yöneten bir sunucuda bu fark, saniyede işlenebilecek istek sayısını doğrudan etkiler.

DEEine weitere wichtige Verwendung von Rot-Schwarz-Bäumen ist das epoll-Subsystem des Kernels — der Mechanismus aus §11, der große Mengen an Dateideskriptoren effizient überwacht. Wenn eine Anwendung epoll_ctl(EPOLL_CTL_ADD, fd, ...) aufruft, um Tausende Sockets zu einer einzigen epoll-Instanz hinzuzufügen, hält der Kernel diese Deskriptoren — eine Menge, die schnelles Hinzufügen, Entfernen und Nachschlagen benötigt — wieder in einem Rot-Schwarz-Baum. Das ist ein konkretes Beispiel dafür, wie sich die Wahl der Datenstruktur direkt auf die Systemaufruf-Performance auswirkt: würde der Kernel stattdessen eine einfache verkettete Liste verwenden, würden sich die Kosten jedes epoll_ctl-Aufrufs linear (O(n)) mit der Anzahl überwachter Deskriptoren erhöhen, während der Rot-Schwarz-Baum das auf O(log n) senkt — auf einem Server, der Zehntausende gleichzeitiger Verbindungen verwaltet, wirkt sich dieser Unterschied direkt auf die Anzahl der pro Sekunde verarbeitbaren Anfragen aus.

💡 Tip: whenever you see "self-balancing tree" in kernel context, ask what ordered operation it enables — CFS needs "smallest vruntime," epoll needs "does this fd already exist"; the tree is chosen because the workload needs ordering or fast membership testing, not just because O(log n) sounds good in the abstract.
💡 İpucu: çekirdek bağlamında "kendi kendini dengeleyen ağaç" gördüğünde, hangi sıralı işlemi mümkün kıldığını sor — CFS "en küçük vruntime"a, epoll "bu fd zaten var mı"ya ihtiyaç duyar; ağaç, soyut olarak O(log n) kulağa hoş geldiği için değil, iş yükü sıralama ya da hızlı üyelik testi gerektirdiği için seçilir.
💡 Hinweis: wenn du im Kernel-Kontext "selbstbalancierender Baum" siehst, frage, welche geordnete Operation er ermöglicht — CFS braucht "kleinstes vruntime", epoll braucht "existiert dieses fd bereits"; der Baum wird gewählt, weil die Arbeitslast Ordnung oder schnelle Zugehörigkeitsprüfung braucht, nicht weil O(log n) abstrakt gut klingt.

kavram Hash Tables — Hash tabloları— Hash-Tabellen

For key-based lookups that need average O(1) time (for example PID → task_struct, or inode number → inode object), the kernel uses hash tables. <linux/hashtable.h> offers a simple but effective hash-table implementation built on a fixed-size bucket array with a list_head in each bucket (to chain colliding items together). Hash-function quality is critical: a poorly distributed hash function can pile most items into a handful of buckets, turning the expected O(1) into an actual O(n) — this is a design concern the kernel's hash-table implementations take seriously.

TRAnahtar bazlı, ortalama O(1) arama gerektiren durumlarda (örneğin PID'den task_struct'a, ya da bir inode numarasından inode nesnesine hızlı erişim) çekirdek hash tablolarını kullanır. <linux/hashtable.h>, sabit boyutlu bir kova (bucket) dizisi ve her kovada bir list_head (çakışan — collision yaşayan — öğeleri zincirleme yöntemiyle tutmak için) temelinde basit ama etkili bir hash tablosu implementasyonu sunar. Hash fonksiyonunun kalitesi kritiktir: kötü dağılan bir hash fonksiyonu, çoğu öğeyi birkaç kovada toplayarak O(1) beklentisini pratikte O(n)'e dönüştürebilir — bu, çekirdek hash tablosu tasarımında dikkatle ele alınan bir konudur.

DEFür schlüsselbasierte Abfragen, die durchschnittlich O(1)-Zeit benötigen (z. B. PID → task_struct, oder Inode-Nummer → Inode-Objekt), verwendet der Kernel Hash-Tabellen. <linux/hashtable.h> bietet eine einfache, aber effektive Hash-Tabellen-Implementierung auf Basis eines Buckets-Arrays fester Größe mit einem list_head in jedem Bucket (um kollidierende Elemente per Verkettung zu halten). Die Qualität der Hash-Funktion ist entscheidend: eine schlecht verteilte Hash-Funktion kann die meisten Elemente in wenigen Buckets anhäufen und die erwartete O(1) praktisch in O(n) verwandeln — ein Aspekt, den das Design der Kernel-Hash-Tabellen sorgfältig berücksichtigt.

💡 Tip: "average O(1)" is doing a lot of work in that sentence — it's an average over a well-distributed key set, not a guarantee; §17.10 puts a concrete number on what happens when that assumption breaks down.
💡 İpucu: "ortalama O(1)" ifadesindeki "ortalama" kelimesi çok şey taşır — bu, iyi dağılmış bir anahtar kümesi üzerinden bir ortalamadır, bir garanti değildir; Bölüm 17.10, bu varsayım bozulduğunda ne olduğuna somut bir rakam koyar.
💡 Hinweis: "durchschnittlich O(1)" trägt in diesem Satz viel Gewicht — es ist ein Durchschnitt über eine gut verteilte Schlüsselmenge, keine Garantie; §17.10 setzt eine konkrete Zahl darauf, was passiert, wenn diese Annahme nicht mehr zutrifft.

evrim & gözlem The Radix Tree and XArray — Radix ağacı ve XArray— Der Radix-Baum und XArray

The page cache (§7) must map a file's potentially millions of pages, by page index (offset / PAGE_SIZE), to a physical page — quickly. A plain hash table is not a good fit here because sequential access (a file's consecutive pages) and range queries (finding all pages within a given range) both need to be supported. Traditionally this used a radix tree — a tree that branches on the bits/digits of the key (index). In modern kernel versions the radix tree has largely been replaced by XArray (<linux/xarray.h>), which offers a simpler API and better cache performance; XArray is designed for a similar purpose (mapping an integer index to a pointer) but encapsulates its internal implementation details more cleanly, a more modern abstraction.

TRSayfa önbelleği (Bölüm 7), bir dosyanın milyonlarca sayfasını, sayfa indeksinden (offset / PAGE_SIZE) fiziksel sayfaya hızlı biçimde eşlemek zorundadır. Basit bir hash tablosu bunun için uygun değildir çünkü sıralı erişim (bir dosyanın ardışık sayfaları) ve aralık sorguları (belirli bir aralıktaki tüm sayfaları bulma) desteklenmelidir. Bunun için geleneksel olarak radix ağacı (radix tree) kullanılırdı — anahtarın (indeksin) bitlerini/basamaklarını kullanarak dallanan bir ağaç yapısı. Modern çekirdek sürümlerinde radix ağacı, daha basit bir API ve daha iyi önbellek performansı sunan XArray (<linux/xarray.h>) ile büyük ölçüde değiştirilmiştir; XArray, benzer bir amaç için (tamsayı indeksten işaretçiye eşleme) tasarlanmış ama iç implementasyon detaylarını daha iyi kapsülleyen modern bir soyutlamadır.

DEDer Seiten-Cache (§7) muss die potenziell Millionen Seiten einer Datei, nach Seitenindex (Offset / PAGE_SIZE), schnell auf eine physische Seite abbilden. Eine einfache Hash-Tabelle passt hier nicht gut, weil sequenzieller Zugriff (aufeinanderfolgende Seiten einer Datei) und Bereichsabfragen (alle Seiten in einem bestimmten Bereich finden) unterstützt werden müssen. Traditionell wurde dafür ein Radix-Baum verwendet — eine Baumstruktur, die anhand der Bits/Ziffern des Schlüssels (Index) verzweigt. In modernen Kernel-Versionen wurde der Radix-Baum größtenteils durch XArray (<linux/xarray.h>) ersetzt, das eine einfachere API und bessere Cache-Performance bietet; XArray ist für einen ähnlichen Zweck (Abbildung eines Integer-Index auf einen Zeiger) konzipiert, kapselt aber seine internen Implementierungsdetails sauberer — eine modernere Abstraktion.

derinlemesine Use Alongside RCU — RCU ile birlikte kullanım— Verwendung zusammen mit RCU

The RCU (Read-Copy-Update) technique from §12 is frequently paired with RCU-protected variants of these structures (especially lists and hash tables) — functions like list_add_rcu() and hlist_add_head_rcu(). These functions apply special memory-ordering (memory-barrier) discipline while adding/removing an item, guaranteeing that concurrent readers (traversing without taking any lock) never observe an inconsistent (half-updated) structure — the data structure and the synchronization technique are designed here in an interlocking way.

TRBölüm 12'de gördüğümüz RCU (Read-Copy-Update) tekniği, genellikle bu veri yapılarının (özellikle liste ve hash tablosu) RCU-korumalı varyantlarıyla birlikte kullanılır (list_add_rcu(), hlist_add_head_rcu() gibi). Bu fonksiyonlar, bir öğe eklerken/çıkarırken, eşzamanlı okuyucuların (hiçbir kilit almadan geçiş yapan) asla tutarsız (yarı güncellenmiş) bir yapı görmemesini garanti eden özel bellek sıralama (memory barrier) disiplinleri içerir — veri yapısı ve senkronizasyon tekniği burada iç içe geçmiş biçimde tasarlanmıştır.

DEDie RCU-Technik (Read-Copy-Update) aus §12 wird häufig zusammen mit RCU-geschützten Varianten dieser Strukturen (besonders Listen und Hash-Tabellen) verwendet — Funktionen wie list_add_rcu() und hlist_add_head_rcu(). Diese Funktionen wenden beim Hinzufügen/Entfernen eines Elements eine spezielle Speicherordnungsdisziplin (Memory Barriers) an, die garantiert, dass gleichzeitige Leser (die ohne jedes Lock traversieren) niemals eine inkonsistente (halb aktualisierte) Struktur sehen — Datenstruktur und Synchronisationstechnik sind hier ineinander verzahnt konzipiert.

💡 Tip: if you see _rcu appended to a list/hash function name, treat it as a signal that this structure is meant to be read without locking — mixing an RCU-protected writer path with a non-RCU-aware reader (or vice versa) reintroduces exactly the race conditions RCU exists to avoid.
💡 İpucu: bir liste/hash fonksiyonu adının sonunda _rcu görürsen, bunu bu yapının kilitlemeden okunmak üzere tasarlandığının işareti olarak al — RCU korumalı bir yazma yolunu RCU'dan habersiz bir okuyucuyla (ya da tersini) karıştırmak, RCU'nun tam olarak önlemek için var olduğu yarış durumlarını geri getirir.
💡 Hinweis: siehst du _rcu am Ende eines Listen-/Hash-Funktionsnamens, deute das als Signal, dass diese Struktur ohne Locking gelesen werden soll — einen RCU-geschützten Schreibpfad mit einem RCU-unwissenden Leser zu mischen (oder umgekehrt) bringt genau die Race Conditions zurück, die RCU eigentlich vermeiden soll.

derinlemesine Deep Dive: the container_of Macro — Key to Embedded Data Structures — Derinlemesine: container_of makrosu — gömülü veri yapılarının anahtarı— Vertiefung: das container_of-Makro — Schlüssel zu eingebetteten Datenstrukturen

§17.7's lab showed container_of()'s pointer arithmetic; here's why the macro sits at the very center of kernel design. The kernel's data-structure philosophy runs opposite to what's habitual in user-space programming: user space usually builds linked lists on a "every node carries its own data" logic (struct node { int data; struct node *next; }), but the struct list_head pattern from §17.2 does the exact opposite — the link node doesn't wrap the data, it is embedded inside the data structure. A task_struct directly contains a struct list_head tasks field; that field carries no data at all, it only holds pointers to the previous and next nodes.

TR17.7'deki laboratuvar, container_of()'un pointer aritmetiğini göstermişti; burada makronun neden çekirdek tasarımının bu kadar merkezinde olduğuna bakalım. Çekirdeğin veri yapısı felsefesi, kullanıcı alanı programlamasında alışılmış olandan tersine işler: kullanıcı alanı genellikle "her düğüm kendi verisini taşır" mantığıyla bağlı listeler kurar (struct node { int data; struct node *next; }), ama Bölüm 17.2'de görülen struct list_head deseni tam tersini yapar — bağlantı düğümü, veriyi sarmalamaz, veri yapısının içine gömülür. Bir süreç tanımlayıcısı (task_struct) içinde doğrudan bir struct list_head tasks alanı bulunur; bu alan hiçbir veri taşımaz, sadece önceki ve sonraki düğümlere işaretçi tutar.

DEDas Labor aus §17.7 zeigte die Zeigerarithmetik von container_of(); hier sehen wir, warum das Makro so zentral im Kernel-Design steht. Die Datenstruktur-Philosophie des Kernels funktioniert umgekehrt zu dem, was in der Userspace-Programmierung üblich ist: Userspace baut verkettete Listen meist nach der Logik "jeder Knoten trägt seine eigenen Daten" (struct node { int data; struct node *next; }), aber das struct list_head-Muster aus §17.2 tut genau das Gegenteil — der Verbindungsknoten umschließt die Daten nicht, er wird in die Datenstruktur eingebettet. Eine task_struct enthält direkt ein Feld struct list_head tasks; dieses Feld trägt überhaupt keine Daten, es hält nur Zeiger auf den vorherigen und nächsten Knoten.

This design's advantage rests on a guarantee provided by offsetof(): a field's byte offset from the start of its containing struct is fixed at compile time and can be computed via offsetof(type, member). The macro container_of(ptr, type, member) reverses this: given only a pointer to the embedded list_head field, it subtracts that offset from the pointer to get back to the start address of the whole task_struct. As a result, the same struct list_head type — with no template or generics mechanism, using pure C — can be reused to link processes, memory regions, file-system entries, and hundreds of other different data types into a linked list. This is a technique that solves the problem C++'s or Java's generic collections solve, but with zero runtime cost, using pure pointer arithmetic.

TRBu tasarımın avantajı, offsetof() makrosunun sağladığı bir garantiye dayanır: bir yapı içindeki bir alanın, yapının başlangıcına göre bayt cinsinden konumu, derleme zamanında sabittir ve offsetof(type, member) ile hesaplanabilir. container_of(ptr, type, member) makrosu bunu tersine çevirir: elimizde sadece gömülü list_head alanına bir işaretçi varken, bu ofseti işaretçiden çıkararak, tüm task_struct'ın başlangıç adresine geri döner. Sonuç olarak, aynı struct list_head tipi — hiçbir şablon (template) ya da genel programlama (generics) mekanizması olmadan, saf C ile — süreçleri, bellek bölgelerini, dosya sistemi girdilerini ve daha yüzlerce farklı veri tipini bağlı listeye almak için yeniden kullanılabilir. Bu, C++ veya Java'daki generic koleksiyonların çözdüğü sorunu, çalışma zamanı maliyeti olmadan, saf işaretçi aritmetiğiyle çözen bir tekniktir.

DEDer Vorteil dieses Designs beruht auf einer von offsetof() gelieferten Garantie: die Byte-Position eines Felds relativ zum Anfang seiner enthaltenden Struktur ist zur Kompilierzeit fest und lässt sich mit offsetof(type, member) berechnen. Das Makro container_of(ptr, type, member) kehrt das um: hat man nur einen Zeiger auf das eingebettete list_head-Feld, zieht man diesen Offset vom Zeiger ab, um zur Startadresse der gesamten task_struct zurückzukommen. Im Ergebnis kann derselbe Typ struct list_head — ohne jedes Template oder Generics-Mechanismus, in reinem C — wiederverwendet werden, um Prozesse, Speicherregionen, Dateisystemeinträge und hunderte weitere unterschiedliche Datentypen in eine verkettete Liste aufzunehmen. Das ist eine Technik, die das Problem löst, das generische Collections in C++ oder Java lösen — aber ohne Laufzeitkosten, mit reiner Zeigerarithmetik.

The risk lives here too: container_of() performs no compile-time type checking — pass the wrong type or member argument and the compiler won't complain, but the resulting pointer causes memory corruption at run time. This is why raw container_of() calls are almost never hand-written in kernel source; instead, helper macros like list_for_each_entry(), which fuse the loop logic with container_of(), are used — this both reduces the error risk and makes the intent ("walk every task_struct in this list") more readable in the code itself.

TRRiski de burada yatar: container_of() derleme zamanında tip kontrolü yapmaz — yanlış type veya member parametresi verilirse, derleyici hata vermez, ama çalışma zamanında bellek bozulmasına yol açan bir işaretçi üretilir. Bu yüzden çekirdek kaynak kodunda container_of() çağrıları neredeyse hiç elle yazılmaz; bunun yerine list_for_each_entry() gibi, döngü mantığını container_of() ile birleştiren yardımcı makrolar kullanılır — bu da hem hata riskini azaltır hem de niyeti ("bu listedeki her task_struct'ı gez") kodun kendisinde daha okunaklı kılar.

DEHier liegt auch das Risiko: container_of() führt keine Typprüfung zur Kompilierzeit durch — übergibt man ein falsches type- oder member-Argument, meldet der Compiler keinen Fehler, aber der entstehende Zeiger verursacht zur Laufzeit Speicherkorruption. Deshalb werden rohe container_of()-Aufrufe im Kernel-Quellcode fast nie von Hand geschrieben; stattdessen kommen Hilfsmakros wie list_for_each_entry() zum Einsatz, die die Schleifenlogik mit container_of() verschmelzen — das reduziert sowohl das Fehlerrisiko als auch macht es die Absicht ("gehe jede task_struct in dieser Liste durch") im Code selbst lesbarer.

💡 Tip: if you ever write a raw container_of() call by hand in real kernel-style code, treat that as a signal to stop and check whether an existing iterator macro (list_for_each_entry() and friends) already does the job more safely.
💡 İpucu: gerçek çekirdek tarzı kodda elle ham bir container_of() çağrısı yazdığını fark edersen, bunu dur ve zaten var olan bir yineleyici makronun (list_for_each_entry() ve benzerleri) işi daha güvenli şekilde yapıp yapmadığını kontrol etme sinyali olarak al.
💡 Hinweis: schreibst du in echtem Kernel-Stil-Code jemals von Hand einen rohen container_of()-Aufruf, sieh das als Signal, innezuhalten und zu prüfen, ob ein bestehendes Iterator-Makro (list_for_each_entry() und Verwandte) die Aufgabe nicht schon sicherer erledigt.

genişletilmiş Extended Look: Bitmaps and Efficient Set Representation — Genişletilmiş inceleme: bitmap'ler ve verimli küme temsili— Erweiterte Betrachtung: Bitmaps und effiziente Mengendarstellung

On top of the structures seen in this chapter, the kernel often needs to "efficiently represent membership in a set" — for example which CPUs on the system are active (cpumask), which signals are pending (§9.4), which memory pages are free. For needs like these the kernel uses the bitmap data structure — every bit represents the presence/absence of one member in a set. Set operations on a bitmap (union, intersection, difference) map directly onto hardware's native bit-level operations (AND, OR, XOR), making bitmaps both extremely compact in memory (1 bit/member) and extremely fast operationally (a single CPU instruction can process 64 members at once).

TRBölüm 17'de gördüğümüz veri yapılarına ek olarak, çekirdek sık sık "bir küme içindeki üyeliği verimli biçimde temsil etme" ihtiyacı duyar — örneğin sistemdeki hangi CPU'ların aktif olduğu (cpumask), hangi sinyallerin bekleyen olduğu (Bölüm 9.4), hangi bellek sayfalarının boş olduğu. Bu tür ihtiyaçlar için çekirdek bitmap veri yapısını kullanır — her bit, kümedeki bir üyenin varlığını/yokluğunu temsil eder. Bir bitmap üzerinde küme işlemleri (birleşim, kesişim, fark) donanımın doğal bit-düzeyi işlemleriyle (AND, OR, XOR) doğrudan eşleşir, bu da onları hem bellek açısından son derece kompakt (1 bit/üye) hem de işlemsel olarak son derece hızlı (bir CPU komutu, 64 üyeyi aynı anda işleyebilir) yapar.

DEZusätzlich zu den in diesem Kapitel gesehenen Strukturen braucht der Kernel oft die Möglichkeit, "Mitgliedschaft in einer Menge effizient darzustellen" — etwa welche CPUs im System aktiv sind (cpumask), welche Signale ausstehen (§9.4), welche Speicherseiten frei sind. Für solche Bedürfnisse verwendet der Kernel die Bitmap-Datenstruktur — jedes Bit repräsentiert die An-/Abwesenheit eines Mitglieds in einer Menge. Mengenoperationen auf einer Bitmap (Vereinigung, Schnittmenge, Differenz) entsprechen direkt den nativen Bit-Operationen der Hardware (AND, OR, XOR), was Bitmaps sowohl speicherseitig extrem kompakt (1 Bit/Mitglied) als auch operativ extrem schnell macht (ein einziger CPU-Befehl kann 64 Mitglieder gleichzeitig verarbeiten).

The cpumask structure is especially instructive: everything discussed in §3.6's CPU affinity and §3.11's load balancing ultimately represents, behind the scenes, "which CPUs are 'eligible' for a given task" using this bitmap structure — the CPU set that sched_setaffinity() receives from user space is represented directly inside the kernel as a cpumask.

TRcpumask yapısı özellikle öğreticidir: Bölüm 3.6'daki CPU yakınlığı ve Bölüm 3.11'deki yük dengeleme tartışmalarının hepsi, arka planda hangi CPU'ların bir görev için "uygun" olduğunu temsil etmek için bu bitmap yapısını kullanır — sched_setaffinity() çağrısının kullanıcı alanından aldığı CPU kümesi, çekirdek içinde doğrudan bir cpumask olarak temsil edilir.

DEDie cpumask-Struktur ist besonders lehrreich: alles, was in §3.6 über CPU-Affinität und in §3.11 über Lastverteilung besprochen wurde, stellt im Hintergrund letztlich mit dieser Bitmap-Struktur dar, welche CPUs für einen bestimmten Task "geeignet" sind — die CPU-Menge, die sched_setaffinity() aus dem Userspace erhält, wird im Kernel direkt als cpumask dargestellt.

This comparison explains why the kernel picks different data structures for the same "lookup" problem in different contexts: the CFS scheduler (§3.2) needs ordered access (smallest vruntime) and so uses a red-black tree, while pure key-value mappings like PID → task_struct favor a hash table — there is no single "fastest" data structure in the abstract, the right answer always depends on the access pattern.

TRBu karşılaştırma, çekirdeğin neden aynı "arama" problemi için farklı bağlamlarda farklı veri yapıları seçtiğini açıklar: CFS zamanlayıcı (Bölüm 3.2) sıralı erişime (en küçük vruntime) ihtiyaç duyduğu için kırmızı-siyah ağaç kullanırken, PID'den task_struct'a erişim gibi saf anahtar-değer eşlemeleri için hash tablosu tercih edilir — "en hızlı" veri yapısı diye tek bir cevap yoktur, doğru cevap her zaman erişim örüntüsüne bağlıdır.

DEDieser Vergleich erklärt, warum der Kernel für dasselbe "Lookup"-Problem in unterschiedlichen Kontexten unterschiedliche Datenstrukturen wählt: der CFS-Scheduler (§3.2) braucht geordneten Zugriff (kleinstes vruntime) und verwendet daher einen Rot-Schwarz-Baum, während reine Schlüssel-Wert-Abbildungen wie PID → task_struct eine Hash-Tabelle bevorzugen — es gibt keine einzige abstrakt "schnellste" Datenstruktur, die richtige Antwort hängt immer vom Zugriffsmuster ab.

💡 Tip: when choosing a data structure for your own code, start from the operation you'll perform most often (exact lookup? ordered traversal? range query? set membership?) rather than from a general reputation for being "fast" — this chapter's structures each win only for the access pattern they were built for.
💡 İpucu: kendi kodun için bir veri yapısı seçerken, "hızlı" olma genel ününden değil, en sık yapacağın işlemden (tam arama mı? sıralı gezinme mi? aralık sorgusu mu? küme üyeliği mi?) yola çık — bu bölümdeki her veri yapısı yalnızca inşa edildiği erişim örüntüsü için kazanır.
💡 Hinweis: wähle eine Datenstruktur für eigenen Code ausgehend von der Operation, die du am häufigsten ausführst (exakte Suche? geordnete Traversierung? Bereichsabfrage? Mengenzugehörigkeit?), nicht ausgehend vom allgemeinen Ruf "schnell" zu sein — jede Struktur dieses Kapitels gewinnt nur für das Zugriffsmuster, für das sie gebaut wurde.
proje 1/3 Find the Degraded Hash Table — bozulmuş hash tablosunu bul— Die degradierte Hash-Tabelle finden

Your home directory contains veri-yapisi-kaydi.txt, a snapshot of the kernel's live data-structure registry: each line has four space-separated fields — type (LIST/RBTREE/HASH/XARRAY), name, status, element count. As in §17.4's discussion of a poorly distributed hash function, exactly one entry here is stuck in degraded status. Use grep degraded veri-yapisi-kaydi.txt to isolate it and redirect the output to bozulmus-hash-tablosu.txt. The grader checks that the file exists and contains the degraded structure inode_tablosu.

TREv dizininde çekirdeğin canlı veri yapısı kaydının bir anlık görüntüsü olan veri-yapisi-kaydi.txt var: her satırda boşlukla ayrılmış dört alan bulunur — tür (LIST/RBTREE/HASH/XARRAY), ad, durum, eleman sayısı. Bölüm 17.4'teki kötü dağılan hash fonksiyonu tartışmasındaki gibi, burada tam olarak bir kayıt degraded durumunda takılı kalmış. grep degraded veri-yapisi-kaydi.txt ile onu ayıkla ve çıktıyı bozulmus-hash-tablosu.txt'ye yönlendir. Değerlendirici, dosyanın var olduğunu ve bozulan yapının inode_tablosu olduğunu kontrol eder.

In each line of veri-yapisi-kaydi.txt, the structure type is the first space-separated field. Use cut -d' ' -f1 to extract that column, then pipe through sort and uniq, redirecting the result to benzersiz-veri-yapisi-turleri.txt. The grader checks that the file exists and contains all four types from this chapter: LIST, RBTREE, HASH and XARRAY.
