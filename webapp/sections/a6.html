temel kavram The Kernel's Own Memory Problem — Çekirdeğin kendi bellek sorunu— Das eigene Speicherproblem des Kernels

Ch. 5 covered how processes get memory through virtual memory. But the kernel itself constantly demands memory too: a fresh task_struct for every new process, a network packet buffer (sk_buff) for every arriving packet, a structure for every open file descriptor — all of these are in-kernel data structures served by the kernel's own allocators. Those allocators live under constraints that user-space malloc() never faces: in some contexts (interrupt handlers) sleeping/blocking is strictly forbidden, allocation must be extremely fast, and external fragmentation must be minimized — because kernel memory is, with few exceptions, non-swappable. Picture a network driver on a system receiving millions of packets per second: it must allocate one sk_buff per packet, inside an interrupt handler where sleeping is illegal, in well under a microsecond — and if the allocation fails, the packet is simply dropped, so even the allocator's failure behavior must be predictable. None of the luxuries user-space malloc() enjoys — waiting for the kernel to hand over fresh pages, triggering a page fault, or even killing the process on failure — exist here.

TRBölüm 5'te süreçlerin sanal bellek yoluyla nasıl bellek aldığını gördük. Saniyede milyonlarca paket alan bir sistemdeki ağ kartı sürücüsünü düşün: her paket için bir sk_buff ayırmak zorundadır, uyumanın yasak olduğu bir kesme işleyicisi içinde, mikrosaniyenin çok altında — ve ayırma başarısız olursa paket düşürülür, yani ayırıcının başarısızlık davranışının bile öngörülebilir olması gerekir. Kullanıcı alanı malloc()'unun sahip olduğu lükslerin — çekirdekten yeni sayfa isteyip beklemek, sayfa hatası tetiklemek, hatta başarısızlıkta süreci sonlandırmak — hiçbiri burada mevcut değildir.

DEKapitel 5 zeigte, wie Prozesse über virtuellen Speicher an Speicher kommen. Aber der Kernel selbst fordert ständig Speicher an: ein task_struct für jeden neuen Prozess, ein Netzwerkpaket-Puffer (sk_buff) für jedes ankommende Paket, eine Struktur für jeden offenen Dateideskriptor — all das sind kernelinterne Datenstrukturen aus den eigenen Allokatoren des Kernels. Diese Allokatoren unterliegen Einschränkungen, die das malloc() des Userspace nie kennt: in manchen Kontexten (Interrupt-Handlern) ist Schlafen/Blockieren strikt verboten, die Allokation muss extrem schnell sein, und externe Fragmentierung muss minimiert werden — denn Kernel-Speicher ist mit wenigen Ausnahmen nicht auslagerbar. Man stelle sich einen Netzwerktreiber auf einem System mit Millionen Paketen pro Sekunde vor: er muss pro Paket ein sk_buff allokieren, in einem Interrupt-Handler, deutlich unter einer Mikrosekunde — und schlägt die Allokation fehl, wird das Paket verworfen; selbst das Fehlverhalten des Allokators muss also vorhersehbar sein.

Why is kernel memory kept non-swappable? The reason is circular: the swap mechanism itself is kernel code. If the kernel's critical data structures could be swapped out, performing a swap operation might first require reading back a swapped-out structure — a classic deadlock scenario. So kernel memory stays resident in physical RAM, and every byte of it is a real, unreclaimable resource. This is precisely why a memory leak inside the kernel is far more serious than one in user space: there is no address space that gets cleaned up automatically when a process exits — leaked kernel memory is gone until the system reboots.

mekanizma The Buddy System: Physical Page Allocator — Buddy sistemi: fiziksel sayfa ayırıcısı— Das Buddy-System: physischer Seitenallokator

At the lowest level, Linux manages physical pages with the buddy allocator. Free pages are kept in free lists organized by power-of-two block sizes (1, 2, 4, 8… pages — "order 0" through "order 10"). When a request arrives, the closest suitable block is found; if it's larger than needed, it is split in half (creating a "buddy" pair) — one half is used, the other joins the free list of the appropriate size. When a block is freed, the kernel checks whether its buddy is also free; if so, the two are merged (coalescing), so fragmentation is reduced over time. The elegance is in the cost: a block's buddy address is computed instantly by flipping a single bit of the block address (an XOR) — no searching required. The price for that elegance is internal fragmentation from the power-of-two constraint: a request for 5 pages must be served with an 8-page block, wasting 3 pages. This layer is what kmalloc() ultimately rests on, and /proc/buddyinfo shows how many free blocks exist per size class — the primary diagnostic file for memory fragmentation.

TREn alt seviyede Linux, fiziksel sayfaları buddy ayırıcısı (buddy allocator) ile yönetir. Boş sayfalar, 2'nin kuvvetleri büyüklüğünde bloklar (1, 2, 4, 8… sayfa — "order 0"dan "order 10"a) halinde serbest listelerde tutulur. Bir istek geldiğinde, uygun en yakın blok bulunur; blok gerekenden büyükse ikiye bölünür ("buddy" çifti oluşur) — yarısı kullanılır, diğer yarısı uygun boyuttaki serbest listeye eklenir. Bir blok serbest bırakıldığında çekirdek, onun "arkadaşının" (buddy) da boş olup olmadığını kontrol eder; öyleyse ikisi birleştirilir (coalescing) ve parçalanma zamanla azalır. Zarafet maliyetindedir: bir bloğun arkadaşının adresi, blok adresinin tek bir bit'inin çevrilmesiyle (XOR işlemi) anında hesaplanır — arama gerekmez. Bu zarafetin bedeli ise 2'nin kuvvetleri kısıtından doğan iç parçalanmadır: 5 sayfalık bir istek, 8 sayfalık bir blokla karşılanmak zorundadır ve 3 sayfa boşa gider. kmalloc()'un dahili olarak dayandığı temel katman budur; /proc/buddyinfo, her boyut sınıfında kaç boş blok bulunduğunu gösterir — bellek parçalanmasının teşhisinde birincil dosyadır.

DEAuf der untersten Ebene verwaltet Linux physische Seiten mit dem Buddy-Allokator. Freie Seiten liegen in Freilisten, organisiert nach Zweierpotenz-Blockgrößen (1, 2, 4, 8… Seiten — "Order 0" bis "Order 10"). Bei einer Anfrage wird der passendste Block gefunden; ist er größer als nötig, wird er halbiert (ein "Buddy"-Paar entsteht) — eine Hälfte wird genutzt, die andere kommt in die Freiliste der passenden Größe. Beim Freigeben prüft der Kernel, ob der Buddy des Blocks ebenfalls frei ist; wenn ja, werden beide verschmolzen (Coalescing), sodass Fragmentierung mit der Zeit abnimmt. Die Eleganz liegt in den Kosten: die Buddy-Adresse eines Blocks wird durch das Umklappen eines einzigen Bits (XOR) sofort berechnet — keine Suche nötig. Der Preis dafür ist interne Fragmentierung durch die Zweierpotenz-Beschränkung: eine Anfrage über 5 Seiten muss mit einem 8-Seiten-Block bedient werden, 3 Seiten gehen verloren. Auf dieser Schicht ruht letztlich kmalloc(); /proc/buddyinfo zeigt die freien Blöcke pro Größenklasse — die primäre Diagnosedatei für Speicherfragmentierung.

On long-running systems the real problem is external fragmentation: total free memory can be plentiful, yet a constant allocate/free churn scatters it into small pieces, and a request for a large contiguous block fails. cat /proc/buddyinfo shows this directly: each row is a memory zone, each column a size class (order 0 = 1 page … order 10 = 1024 pages). Big numbers in the left columns and zeros on the right mean the system is fragmented — 4 KB allocations keep working while huge page (§5.8) or large DMA buffer requests start failing. The kernel counters this with memory compaction: movable pages are herded to one end of memory to open large contiguous holes, and it can be triggered manually by writing to /proc/sys/vm/compact_memory. The zone structure itself is hardware-driven: ZONE_DMA (the first 16 MB reachable by ancient ISA devices), ZONE_DMA32 (the first 4 GB for devices that can only produce 32-bit physical addresses), and ZONE_NORMAL (everything else). Each zone keeps its own buddy free lists, and DMA-capable buffers must come from the right zone (via GFP_DMA/GFP_DMA32). On NUMA systems this multiplies once more: every NUMA node has its own set of zones, observable per node via numastat or /sys/devices/system/node/node*/meminfo.

TRUzun süre çalışan sistemlerde asıl sorun dış parçalanmadır: toplam boş bellek bol olsa bile, sürekli ayırma/serbest bırakma döngüsü bu belleği küçük parçalara dağıtır ve büyük bitişik bir blok isteği başarısız olur. cat /proc/buddyinfo bunu doğrudan gösterir: her satır bir bellek bölgesi (zone), her sütun bir boyut sınıfıdır (order 0 = 1 sayfa … order 10 = 1024 sayfa). Çekirdek buna bellek yoğunlaştırma (memory compaction) ile karşılık verir: hareket ettirilebilir sayfalar belleğin bir ucuna toplanarak büyük bitişik boşluklar açılır; /proc/sys/vm/compact_memory dosyasına yazarak elle de tetiklenebilir. Bölge yapısının kendisi tamamen donanım kaynaklıdır: ZONE_DMA (eski ISA aygıtlarının erişebildiği ilk 16 MB), ZONE_DMA32 (yalnızca 32-bit fiziksel adres üretebilen aygıtlar için ilk 4 GB) ve ZONE_NORMAL (geri kalan her şey). Her bölgenin kendi buddy serbest listeleri vardır ve DMA yapılacak arabellekler doğru bölgeden gelmek zorundadır (GFP_DMA/GFP_DMA32 ile). NUMA sistemlerinde bu yapı bir kat daha çoğalır: her NUMA düğümünün kendi bölge takımı vardır ve düğüm başına durum numastat ya da /sys/devices/system/node/node*/meminfo üzerinden izlenir.

DEAuf lange laufenden Systemen ist das eigentliche Problem die externe Fragmentierung: der freie Gesamtspeicher kann reichlich sein, doch ständiges Allokieren/Freigeben verstreut ihn in kleine Stücke, und eine Anfrage nach einem großen zusammenhängenden Block schlägt fehl. cat /proc/buddyinfo zeigt das direkt: jede Zeile ist eine Speicher-Zone, jede Spalte eine Größenklasse (Order 0 = 1 Seite … Order 10 = 1024 Seiten). Große Zahlen links und Nullen rechts bedeuten Fragmentierung — 4-KB-Allokationen funktionieren weiter, während Huge-Page- oder große DMA-Puffer-Anfragen scheitern. Der Kernel kontert mit Memory Compaction: bewegliche Seiten werden an ein Ende des Speichers getrieben, um große zusammenhängende Lücken zu öffnen; manuell auslösbar über /proc/sys/vm/compact_memory. Die Zonenstruktur ist hardwarebedingt: ZONE_DMA (die ersten 16 MB für alte ISA-Geräte), ZONE_DMA32 (die ersten 4 GB für Geräte mit nur 32-Bit-Adressen) und ZONE_NORMAL (der Rest). Jede Zone hat eigene Buddy-Freilisten; DMA-Puffer müssen aus der richtigen Zone kommen (GFP_DMA/GFP_DMA32). mekanizma Slab/SLUB: Small-Object Caching — Slab/SLUB: küçük nesne önbellekleme— Slab/SLUB: Caching kleiner Objekte

The buddy system works at page (4 KB) granularity, but the kernel mostly needs much smaller, fixed-size objects: a task_struct is a few KB, an inode structure smaller still. Allocating a full page per tiny object would be both slow and wasteful. The slab allocator — and its modern, simplified variant SLUB, the default on today's Linux — keeps pre-built "caches" for frequently used object types: each cache takes pages from the buddy system, slices them into equal-size objects, and hands those objects out and takes them back very fast. A key side benefit is object reuse: when an object is freed, its structure usually stays in the cache without being zeroed; the next request for the same type can reuse that memory directly. That keeps hot data structures "warm" in the CPU cache — allocator design and CPU-cache friendliness meet here.

TRBuddy sistemi sayfa (4 KB) granülaritesinde çalışır, ama çekirdek çoğunlukla çok daha küçük, sabit boyutlu nesnelere ihtiyaç duyar: bir task_struct birkaç KB'dir, bir inode yapısı daha da küçüktür. Her minik nesne için tam bir sayfa ayırmak hem yavaş hem israflı olurdu. Slab ayırıcısı — ve onun modern, basitleştirilmiş varyantı, günümüz Linux'unda varsayılan olan SLUB — sık kullanılan nesne türleri için önceden yapılandırılmış "önbellekler (cache)" tutar: her önbellek, buddy sisteminden aldığı sayfaları eşit boyutlu nesnelere böler ve bu nesneleri çok hızlı biçimde dağıtıp geri alır. Önemli bir yan fayda nesne yeniden kullanımıdır: bir nesne serbest bırakıldığında yapısı genellikle sıfırlanmadan önbellekte kalır; aynı türde bir sonraki istek bu belleği doğrudan yeniden kullanabilir. Bu, sık kullanılan veri yapılarını CPU önbelleğinde "sıcak" tutar — ayırıcı tasarımı ile CPU önbellek dostluğu burada buluşur.

DEDas Buddy-System arbeitet mit Seiten-Granularität (4 KB), doch der Kernel braucht meist viel kleinere Objekte fester Größe: ein task_struct hat wenige KB, eine Inode-Struktur ist noch kleiner. Pro winzigem Objekt eine ganze Seite zu allokieren wäre langsam und verschwenderisch. Der Slab-Allokator — und seine moderne, vereinfachte Variante SLUB, heute der Linux-Standard — hält vorgefertigte "Caches" für häufig genutzte Objekttypen: jeder Cache nimmt Seiten vom Buddy-System, zerteilt sie in gleich große Objekte und gibt diese sehr schnell aus und zurück. Ein wichtiger Nebeneffekt ist die Objekt-Wiederverwendung: wird ein Objekt freigegeben, bleibt seine Struktur meist unnullifiziert im Cache; die nächste Anfrage desselben Typs kann den Speicher direkt wiederverwenden. So bleiben heiße Datenstrukturen im CPU-Cache "warm".

Real incident — hunting a kernel memory leak: on a long-running server, available memory shrinks over time, yet no user-space process seems responsible (the ps/top totals don't add up to total used memory). Running slabtop shows the count of dentry (directory entry cache) objects growing continuously. Investigation reveals a monitoring tool stat()-ing thousands of temporary file paths every second, while a kernel/filesystem interaction quirk (or overly aggressive caching behavior) keeps the dentry cache from shrinking under memory pressure as it should. echo 2 > /proc/sys/vm/drop_caches brings temporary relief; the durable fix is lowering the monitoring tool's query frequency and tuning the kernel's vfs_cache_pressure parameter. The case shows how in-kernel memory structures are indirectly but powerfully coupled to user-space behavior — and slabtop is the first place to look whenever a kernel memory leak is suspected.

TRGerçek olay — çekirdek bellek sızıntısı avı: uzun süre çalışan bir sunucuda kullanılabilir bellek zamanla azalır ama hiçbir kullanıcı alanı süreci sorumlu görünmez (ps/top toplamı, toplam kullanılan bellekle örtüşmez). slabtop çalıştırıldığında dentry (dizin girdisi önbelleği) nesnelerinin sayısının sürekli arttığı görülür. İnceleme, bir izleme (monitoring) aracının her saniye binlerce geçici dosya yolunu stat() ile sorguladığını, bir çekirdek/dosya sistemi etkileşim tuhaflığının (ya da aşırı agresif önbellekleme davranışının) ise dentry önbelleğinin bellek baskısı altında olması gerektiği gibi küçülmesini engellediğini ortaya çıkarır. echo 2 > /proc/sys/vm/drop_caches geçici rahatlama sağlar; kalıcı çözüm, izleme aracının sorgu sıklığını azaltmak ve çekirdeğin vfs_cache_pressure parametresini ayarlamaktır. Bu vaka, çekirdek içi bellek yapılarının kullanıcı alanı davranışıyla nasıl dolaylı ama güçlü biçimde bağlantılı olduğunu gösterir — ve bir çekirdek bellek sızıntısı şüphesinde ilk bakılacak yer slabtop'tur.

DEEchter Vorfall — Jagd auf ein Kernel-Speicherleck: auf einem lange laufenden Server schrumpft der verfügbare Speicher, doch kein Userspace-Prozess scheint verantwortlich (die ps/top-Summen passen nicht zur Gesamtnutzung). slabtop zeigt, dass die Zahl der dentry-Objekte (Verzeichniseintrags-Cache) kontinuierlich wächst. kmalloc() rests on the slab/buddy stack and returns memory that is physically contiguous — a hard requirement for device drivers doing DMA (Direct Memory Access), because hardware generally doesn't understand virtual addresses; it only works with physical ones. But the physical-contiguity requirement limits kmalloc() for large allocations: in fragmented physical memory, finding a big contiguous block gets hard. vmalloc() provides only virtually contiguous memory: it collects physically scattered pages and stitches them together with consecutive page-table mappings in the kernel's virtual address space. That makes it more reliable for large allocations (it works even in fragmented physical memory), but it is unsuitable for DMA and slightly slower than kmalloc() due to the extra page-table management. The rule of thumb: small and/or DMA-bound allocations → kmalloc(); large, kernel-internal-only allocations (never handed directly to hardware) → vmalloc().

kmalloc() and its relatives take GFP (Get Free Pages) flags that describe how the allocation is allowed to behave. GFP_KERNEL is the normal kernel allocation: it may sleep (block) if needed and may trigger page reclaim — which is exactly why it must never be used in interrupt context. GFP_ATOMIC is for interrupt handlers and any context that cannot sleep: it never blocks, but it may fail if memory isn't immediately available. Finer-grained flags such as GFP_NOWAIT, GFP_NOFS, and GFP_NOIO serve special contexts — for example, an allocation inside a filesystem handler that must not recurse back into filesystem I/O uses GFP_NOFS.

vaka The OOM Killer: Last-Resort Mechanism — OOM Killer: son çare mekanizması— Der OOM-Killer: letzter Ausweg

When system memory is exhausted and the kernel can reclaim nothing more (swap included), the OOM Killer (Out-Of-Memory Killer) steps in and terminates one or more processes to keep the system alive. The victim is chosen by an oom_score assigned to every process, based on its memory usage, runtime, and manual adjustment via /proc/<pid>/oom_score_adj. Critical system services are usually protected by setting oom_score_adj to -1000 (for example sshd, so the administrator never loses access). In production, the first suspect for an unexpected process death is the OOM Killer — confirmed by searching dmesg for "Out of memory: Killed process" lines. A crucial distinction when analyzing OOM events: system-wide OOM vs cgroup OOM. The first covers the whole machine and is a genuine emergency; the second fires when a cgroup (Ch. 18) exceeds its own memory limit and kills only processes inside that cgroup — the rest of the system is untouched. The container-world message "container killed with exit code 137" means exactly this: 137 = 128 + 9, i.e. SIGKILL, almost always from a cgroup memory limit. So when a container restarts unexpectedly, the correct order is dmesg and cgroup memory counters before application logs — the app logs usually show nothing, because SIGKILL cannot be caught and a process cannot log its own death.

Two more pieces complete the OOM picture. First, prevention: the mlock() and mlockall() system calls "pin" specific memory regions in physical RAM so they can never be swapped. Security software holding encryption keys uses this for secrecy (the key must never touch disk); real-time applications use it for predictability (no major page fault may ever occur on the critical path). The amount of lockable memory is bounded by the RLIMIT_MEMLOCK resource limit (ulimit -l) — otherwise any user could pin all physical RAM and paralyze the system. Second, post-mortem skill: reading the anatomy of the OOM report in dmesg. The report contains a memory table of every process at the moment of the event (RSS, page-table size, oom_score_adj), the state of every memory zone, and finally the "Killed process" line naming the victim. A common analysis mistake is treating the victim as the culprit — the OOM Killer may have picked the "biggest" long-lived process, while the memory was actually consumed by another process growing rapidly just before the event; the table must be read line by line, independent of who died. On the preventive-monitoring side, the trend of the available column in free -h and the si/so columns of vmstat 1 can reveal a system drifting toward OOM minutes before it happens — alerting on those thresholds is the cheapest way to keep the OOM Killer off the stage entirely.

Call kmalloc(100, ...) and the kernel actually reserves the next class up (128 bytes) — the 28-byte difference is lost as internal fragmentation. Subsystems that allocate millions of small objects (e.g. network packet processing) therefore often define their own exact-size slab caches with kmem_cache_create() instead of relying on general-purpose kmalloc(). You can observe the classes directly: sudo cat /proc/slabinfo | grep '^kmalloc' shows a separate slab cache per size class, with active objects, total objects, object size, and objects per slab. Beyond less waste, a dedicated cache buys two more things. Diagnosability: the custom cache appears under its own name in slabtop//proc/slabinfo, so a memory increase can be attributed to a specific subsystem — whereas growth in the generic kmalloc-128 cache could belong to any of hundreds of kernel users. And a constructor: a function run when an object is first created can initialize fixed fields (say, a lock structure) once, and that initialization is not repeated when the object is freed and reused — the "hot object reuse" benefit from the slab topic, taken one step further.

Daha az israfın ötesinde, özel bir önbellek iki şey daha kazandırır. Ve bir kurucu fonksiyon (constructor): nesne ilk oluşturulduğunda çalışan bu fonksiyon, sabit alanları (örneğin bir kilit yapısını) bir kez ilklendirir ve nesne serbest bırakılıp yeniden kullanıldığında bu ilklendirme tekrarlanmaz — slab konusundaki "sıcak nesne yeniden kullanımı" faydasının bir adım ileri götürülmüş hali.

evrim & gözlem SLUB's Design Simplifications and kmemleak — SLUB'un tasarım sadeleştirmeleri ve kmemleak— SLUBs Design-Vereinfachungen und kmemleak

SLUB, mentioned in the slab topic, carries important design simplifications over the old SLAB allocator — and understanding why teaches a general lesson of kernel performance engineering. Old SLAB kept complex per-CPU "queues" and many management structures; that overhead became a growing bottleneck as multi-core systems spread (every core's management structures must be kept synchronized). SLUB removes most of that complexity: it keeps minimalist metadata directly in the page structures (struct page) and uses per-CPU local "fastpath" caches to largely avoid locking (Ch. 12). SLUB gave up some of SLAB's advanced features (such as object coloring, a cache-optimization technique) in exchange for a much simpler design that runs faster on modern hardware. The principle generalizes: more features/flexibility does not always mean better design — complexity is always a cost, and when that cost exceeds the benefit it buys, simplification wins.

TRSlab konusunda bahsedilen SLUB, eski SLAB ayırıcısına göre önemli tasarım sadeleştirmeleri taşır — ve nedenlerini anlamak, çekirdek performans mühendisliğinin genel bir dersini verir. Eski SLAB, her CPU için karmaşık "kuyruklar" (queue) ve çok sayıda yönetim yapısı tutuyordu; çok çekirdekli sistemler yaygınlaştıkça (her çekirdeğin yönetim yapılarını senkronize tutma maliyetiyle) bu ek yük giderek büyüyen bir darboğaz haline geldi. SLUB bu karmaşıklığın çoğunu ortadan kaldırır: minimalist metadata'yı doğrudan sayfa yapılarında (struct page) tutar ve CPU başına yerel "hızlı yol" (fastpath) önbellekleriyle kilitleme ihtiyacını (Bölüm 12) büyük ölçüde azaltır. SLUB, SLAB'ın bazı ileri özelliklerinden (nesne renklendirmesi gibi bir önbellek optimizasyon tekniği) feragat ederek, modern donanımda daha hızlı çalışan çok daha basit bir tasarıma ulaştı. İlke geneldir: daha fazla özellik/esneklik her zaman daha iyi tasarım demek değildir — karmaşıklık her zaman bir maliyettir ve bu maliyet sağladığı faydayı aşarsa, sadeleştirme kazandırır.

DESLUB, im Slab-Thema erwähnt, trägt wichtige Design-Vereinfachungen gegenüber dem alten SLAB-Allokator — und das Warum lehrt eine allgemeine Lektion der Kernel-Performance-Technik. Alt-SLAB hielt komplexe Pro-CPU-"Queues" und viele Verwaltungsstrukturen; dieser Overhead wurde mit der Verbreitung von Mehrkernsystemen zum wachsenden Engpass (die Strukturen jedes Kerns müssen synchron gehalten werden). SLUB beseitigt das meiste davon: minimalistische Metadaten direkt in den Seitenstrukturen (struct page) und Pro-CPU-"Fastpath"-Caches, die Locking (Kapitel 12) weitgehend vermeiden. SLUB verzichtete auf einige fortgeschrittene SLAB-Features (etwa Object Coloring, eine Cache-Optimierungstechnik) zugunsten eines viel einfacheren, auf moderner Hardware schnelleren Designs. Das Prinzip verallgemeinert sich: mehr Features/Flexibilität bedeutet nicht automatisch besseres Design — Komplexität ist immer ein Preis, und übersteigt er den Nutzen, gewinnt die Vereinfachung.

The chapter's final tool addresses the hardest problem of all: finding kernel memory leaks. User space has mature leak detectors (Valgrind, AddressSanitizer) that track every allocate/free and report "orphaned" blocks at program exit. The kernel can't do that: it never exits (it runs as long as the system does), so there is no "end of program"; and tracking every allocation in detail on performance-critical paths would slow things unacceptably. The kernel's answer is kmemleak — a special, low-overhead leak detector that periodically scans kernel memory much like a garbage collector would, marking blocks referenced by no reachable pointer as "leak suspects". /sys/kernel/debug/kmemleak lists those suspects. Note the layering relative to the dentry case: slabtop gives the administrator the symptom ("this cache keeps growing"); kmemleak gives the kernel developer the root cause ("this code path leaked that memory").

TRBölümün son aracı, en zor soruna el atar: çekirdek bellek sızıntılarını bulmak. Kullanıcı alanında olgun sızıntı dedektörleri vardır (Valgrind, AddressSanitizer); her ayırma/serbest bırakmayı izler ve program sonunda "sahipsiz" blokları raporlar. Çekirdek bunu yapamaz: asla sonlanmaz (sistem çalıştığı sürece çalışır), yani bir "program sonu" yoktur; ve performans kritik yollarda her ayırmayı ayrıntılı izlemek kabul edilemez bir yavaşlamaya yol açardı. Çekirdeğin cevabı kmemleak'tir — tıpkı bir çöp toplayıcı (garbage collector) gibi, çekirdek belleğini periyodik olarak tarayan ve erişilebilir hiçbir işaretçi tarafından referans verilmeyen blokları "sızıntı şüphelisi" olarak işaretleyen özel, düşük ek yüklü bir sızıntı dedektörü. /sys/kernel/debug/kmemleak dosyası bu şüphelileri listeler. Dentry vakasına göre katmanlamaya dikkat et: slabtop, sistem yöneticisine belirtiyi verir ("bu önbellek sürekli büyüyor"); kmemleak ise çekirdek geliştiricisine kök nedeni verir ("şu kod yolu şu belleği sızdırdı").

DEDas letzte Werkzeug des Kapitels widmet sich dem schwersten Problem: Kernel-Speicherlecks finden. Der Userspace hat reife Leak-Detektoren (Valgrind, AddressSanitizer), die jede Allokation/Freigabe verfolgen und am Programmende "verwaiste" Blöcke melden. Der Kernel kann das nicht: er endet nie (er läuft, solange das System läuft), es gibt also kein "Programmende"; und jede Allokation auf performancekritischen Pfaden detailliert zu verfolgen würde inakzeptabel bremsen. Die Antwort des Kernels ist kmemleak — ein spezieller Leak-Detektor mit geringem Overhead, der den Kernel-Speicher periodisch scannt, ähnlich wie ein Garbage Collector, und Blöcke ohne erreichbare Zeigerreferenz als "Leck-Verdächtige" markiert. /sys/kernel/debug/kmemleak listet diese Verdächtigen. Man beachte die Schichtung gegenüber dem dentry-Fall: slabtop liefert dem Administrator das Symptom ("dieser Cache wächst ständig"); kmemleak liefert dem Kernel-Entwickler die Ursache ("dieser Codepfad hat jenen Speicher geleckt").
