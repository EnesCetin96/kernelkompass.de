Linux System Architecture & Kernel Philosophy

Linux Sistem Mimarisine Giriş ve Çekirdek Felsefesi

Einführung in die Linux-Systemarchitektur und Kernel-Philosophie

Purpose: understand the user space / kernel space divide, why Linux is monolithic-but-modular, the kernel's four core responsibilities, and how each of them has a concrete, observable footprint from user space.

Amaç: kullanıcı alanı / çekirdek alanı ayrımını, Linux'un neden "monolitik ama modüler" olduğunu, çekirdeğin dört temel sorumluluğunu ve her birinin kullanıcı alanından nasıl gözlemlenebildiğini anlamak.

Zweck: die Trennung zwischen User Space und Kernel Space verstehen, warum Linux "monolithisch, aber modular" ist, die vier Kernaufgaben des Kernels kennenlernen und wie jede davon aus dem User Space beobachtbar ist.

✎ Notlarım — Sistem Mimarisi ve Çekirdek Felsefesi

kavram Why Think in Terms of "The Kernel"? — Neden "Çekirdek" merkezli düşünmeliyiz?— Warum kernelzentriert denken?

Think of an operating system as a building. What the user sees — windows, doors, furniture — is application software. What keeps the building standing — the structural frame, the electrical wiring, the plumbing — is invisible; that is exactly what the kernel is. The Linux kernel sits between the hardware and every program running on top of it, sharing resources, isolating processes, and protecting the system.

TRBir işletim sistemini bir bina gibi düşün. Kullanıcının gördüğü kısım — pencereler, kapılar, mobilyalar — uygulama yazılımlarıdır. Ama binanın ayakta durmasını sağlayan taşıyıcı sistem, elektrik tesisatı, su borusu hatları görünmez; işte çekirdek (kernel) tam olarak budur. Linux çekirdeği, donanım ile üzerinde çalışan her programın arasına giren, kaynakları paylaştıran, izole eden ve koruyan bir aracıdır.

DEStell dir ein Betriebssystem wie ein Gebäude vor. Was der Nutzer sieht — Fenster, Türen, Möbel — ist Anwendungssoftware. Was das Gebäude aber trägt — die Tragstruktur, die Elektrik, die Wasserleitungen — bleibt unsichtbar; genau das ist der Kernel. Der Linux-Kernel steht zwischen der Hardware und jedem darauf laufenden Programm, teilt Ressourcen zu, isoliert Prozesse und schützt das System.

A systems programmer's first key lesson is the sharp divide between user space and kernel space. The CPU runs at different privilege levels — x86 calls these "rings": ring 0 is the most privileged, ring 3 the most restricted. The Linux kernel runs in ring 0, ordinary applications in ring 3. When an application wants to read a file, send a network packet, or allocate memory, it cannot touch the hardware directly — it must "ask" the kernel via a system call.

TRBir sistem programcısının ilk öğrenmesi gereken şey, kullanıcı alanı (user space) ile çekirdek alanı (kernel space) arasındaki keskin ayrımdır. İşlemci farklı ayrıcalık seviyelerinde çalışır — x86 mimarisinde bunlara "ring" denir: ring 0 en yetkili, ring 3 en kısıtlı seviyedir. Linux çekirdeği ring 0'da, normal uygulamalar ring 3'te çalışır. Bir uygulama dosya okumak, ağ paketi göndermek ya da bellek ayırmak istediğinde, donanıma doğrudan dokunamaz — bunun yerine bir sistem çağrısı (system call) aracılığıyla çekirdekten bunu "rica eder".

DEDie erste zentrale Lektion für Systemprogrammierer ist die scharfe Trennung zwischen User Space und Kernel Space. Die CPU läuft auf unterschiedlichen Privilegstufen — bei x86 heißen diese "Ringe": Ring 0 ist am privilegiertesten, Ring 3 am eingeschränktesten. Der Linux-Kernel läuft in Ring 0, gewöhnliche Anwendungen in Ring 3. Will eine Anwendung eine Datei lesen, ein Netzwerkpaket senden oder Speicher reservieren, kann sie die Hardware nicht direkt ansprechen — sie muss den Kernel über einen Systemaufruf (System Call) "bitten".

Ring 3 ↔ syscall gate ↔ Ring 0 ↔ Hardware — the syscall boundary is enforced by the CPU itself, not by software convention

This isn't just a software convention — it's a hardware guarantee. On x86-64, the CPU stores the current privilege level (CPL) in the two lowest bits of the code segment (CS) register. User-space code running at CPL=3 that attempts privileged operations — direct I/O port access, changing the page table base register (CR3), editing the interrupt descriptor table (IDT) — triggers a general protection fault (#GP), handing control back to the kernel. ARM calls the same idea "exception levels" (EL0-EL3); RISC-V calls it "privilege modes" (U/S/M) — the names differ, the principle doesn't.

TRBu sadece yazılımsal bir kural değil — donanım tarafından garanti edilir. x86-64'te işlemci, o an hangi ayrıcalık seviyesinde (CPL) çalıştığını CS (kod segmenti) yazmacının en düşük iki bitinde saklar. CPL=3 ile çalışan kullanıcı alanı kodu, G/Ç port komutlarını doğrudan yürütmeye, sayfa tablosu taban yazmacını (CR3) değiştirmeye ya da kesme tanımlayıcı tablosunu (IDT) elden geçirmeye kalkıştığında, işlemci bir genel koruma hatası (#GP) üretir ve kontrolü çekirdeğe devreder. ARM'de aynı fikir "istisna seviyeleri" (EL0-EL3), RISC-V'de "ayrıcalık modları" (U/S/M) olarak adlandırılır — isimler değişse de ilke aynıdır.

DEDas ist keine reine Softwarekonvention — es ist eine Hardware-Garantie. Bei x86-64 speichert die CPU die aktuelle Privilegstufe (CPL) in den beiden niedrigsten Bits des Codesegment-Registers (CS). Versucht User-Space-Code mit CPL=3 privilegierte Operationen — direkte I/O-Port-Zugriffe, Ändern des Seitentabellen-Basisregisters (CR3), Bearbeiten der Interrupt Descriptor Table (IDT) —, löst der Prozessor einen General Protection Fault (#GP) aus und übergibt die Kontrolle an den Kernel. ARM nennt dasselbe Prinzip "Exception Levels" (EL0-EL3), RISC-V "Privilege Modes" (U/S/M) — die Namen unterscheiden sich, das Prinzip nicht.

💡 Tip: a crashed or infinite-looping application can't take down the kernel — process isolation contains it. But if the kernel itself crashes, the whole system goes down ("kernel panic"), which is exactly why kernel code is held to a far stricter discipline than application code.
💡 İpucu: çöken ya da sonsuz döngüye giren bir uygulama çekirdeği düşüremez — süreç izolasyonu onu hapseder. Ama çekirdeğin kendisi çökerse tüm sistem çöker ("kernel panic") — çekirdek kodunun uygulama koduna göre çok daha katı bir disiplinle yazılmasının sebebi tam olarak budur.
💡 Hinweis: eine abgestürzte oder in einer Endlosschleife hängende Anwendung kann den Kernel nicht mitreißen — Prozessisolation hält sie in Schach. Stürzt aber der Kernel selbst ab, fällt das ganze System aus ("Kernel Panic") — genau deshalb wird Kernel-Code nach einer viel strengeren Disziplin geschrieben als Anwendungscode.

mimari Monolithic — But Modular — Monolitik ama modüler— Monolithisch, aber modular

Linux is historically a monolithic kernel: process management, memory management, filesystems, the networking stack, and device drivers all run in the same address space at ring 0. The alternative is a microkernel, where only the bare essentials (messaging, basic scheduling) live in the kernel, and everything else runs as separate user-space processes.

TRLinux, tarihsel olarak monolitik bir çekirdektir: süreç yönetimi, bellek yönetimi, dosya sistemleri, ağ yığını ve aygıt sürücülerinin tamamı aynı adres alanında, ring 0 ayrıcalığıyla çalışır. Bunun alternatifi mikroçekirdek (microkernel) mimarisidir; burada sadece en temel işlevler (mesajlaşma, temel zamanlama) çekirdekte kalır, geri kalan her şey kullanıcı alanında ayrı süreçler olarak çalışır.

DELinux ist historisch ein monolithischer Kernel: Prozessverwaltung, Speicherverwaltung, Dateisysteme, Netzwerk-Stack und Gerätetreiber laufen alle im selben Adressraum mit Ring-0-Rechten. Die Alternative ist eine Mikrokernel-Architektur, bei der nur die absoluten Grundfunktionen (Messaging, einfache Zeitplanung) im Kernel bleiben und alles andere als separate User-Space-Prozesse läuft.

The monolithic approach wins on performance: data flows between, say, a filesystem driver and the memory manager via a direct function call, no expensive message-passing layer required. The cost is a larger attack/failure surface — a bug in any driver can, in theory, endanger the whole kernel. Linux softens this with Loadable Kernel Modules (LKM): drivers can be loaded and unloaded at runtime, keeping the codebase modular even though everything still shares one address space.

TRMonolitik yaklaşımın avantajı performanstır: bir dosya sistemi sürücüsü ile bellek yöneticisi arasında veri aktarımı doğrudan fonksiyon çağrısıyla olur, pahalı mesajlaşma katmanlarına gerek yoktur. Dezavantajı ise güvenlik yüzeyinin büyümesidir: herhangi bir sürücüdeki hata, teorik olarak tüm çekirdeği tehlikeye atabilir. Linux bu dezavantajı yüklenebilir çekirdek modülleri (Loadable Kernel Modules, LKM) ile yumuşatır — sürücüler çalışma zamanında yüklenip kaldırılabilir, kod tabanı modüler tutulur, ama yine de aynı adres alanında çalışırlar.

DEDer monolithische Ansatz gewinnt bei der Performance: Daten fließen etwa zwischen einem Dateisystemtreiber und dem Speicherverwalter über einen direkten Funktionsaufruf, ohne teure Message-Passing-Schicht. Der Nachteil ist eine größere Angriffs-/Fehlerfläche: ein Bug in irgendeinem Treiber kann theoretisch den gesamten Kernel gefährden. Linux mildert das mit Loadable Kernel Modules (LKM): Treiber können zur Laufzeit geladen und entladen werden, die Codebasis bleibt modular, auch wenn alles im selben Adressraum läuft.

You can see this "monolithic-but-modular" balance directly on any distro: /boot/vmlinuz-6.x.x holds the core image, always resident in memory, while hundreds of .ko (kernel object) files under /lib/modules/$(uname -r)/ hold drivers loaded on demand — via udev when hardware is detected, or when a user runs modprobe. This is why one kernel image can serve everything from an embedded board to a server, each machine loading only the modules its own hardware needs.

TRBu "monolitik-ama-modüler" dengeyi herhangi bir dağıtımda doğrudan görebilirsin: /boot/vmlinuz-6.x.x, her zaman bellekte tutulan çekirdek imajını içerirken, /lib/modules/$(uname -r)/ altındaki yüzlerce .ko (kernel object) dosyası ihtiyaç anında yüklenen sürücüleri barındırır — donanım algılandığında udev aracılığıyla, ya da kullanıcı modprobe çalıştırdığında. Bu tasarım sayesinde tek bir çekirdek imajı, gömülü bir karttan sunucuya kadar her şeye hizmet edebilir — her makine yalnızca kendi donanımına özgü modülleri yükler.

DEDieses "monolithisch-aber-modular"-Gleichgewicht siehst du direkt auf jeder Distribution: /boot/vmlinuz-6.x.x enthält das Kernabbild, das immer im Speicher resident ist, während Hunderte von .ko-Dateien (Kernel Object) unter /lib/modules/$(uname -r)/ bei Bedarf geladene Treiber enthalten — über udev bei erkannter Hardware oder wenn ein Nutzer modprobe ausführt. So kann ein einziges Kernabbild von Embedded-Boards bis zu Servern alles bedienen — jede Maschine lädt nur die Module, die ihre eigene Hardware braucht.

bakış açısı Two Perspectives: Systems Programmer vs. Kernel Developer — İki bakış açısı: sistem programcısı ve çekirdek geliştiricisi— Zwei Perspektiven: Systemprogrammierer und Kernel-Entwickler

To a systems programmer, the kernel is mostly a service provider. POSIX system calls like open(), read(), write(), fork(), mmap(), socket() are services the application requests from the kernel. The C standard library (glibc or musl) wraps these calls — most programmers never touch a raw syscall() number directly.

TRBir sistem programcısı için çekirdek çoğunlukla bir hizmet sağlayıcıdır. open(), read(), write(), fork(), mmap(), socket() gibi POSIX sistem çağrıları, uygulamanın çekirdekten talep ettiği hizmetlerdir. C standart kütüphanesi (glibc ya da musl) bu çağrıları sarmalar — programcı çoğu zaman doğrudan syscall() numarasıyla uğraşmaz.

DEFür einen Systemprogrammierer ist der Kernel meist ein Diensteanbieter. POSIX-Systemaufrufe wie open(), read(), write(), fork(), mmap(), socket() sind Dienste, die die Anwendung vom Kernel anfordert. Die C-Standardbibliothek (glibc oder musl) kapselt diese Aufrufe — die meisten Programmierer fassen nie eine rohe syscall()-Nummer direkt an.

A crucial distinction for advanced learners: a system call is not the same thing as a library function. printf() is a library function that buffers internally and eventually triggers a write() syscall. malloc() is a library function that uses brk() or mmap() under the hood — but not every malloc() call becomes a syscall, since glibc serves small allocations from its own internal free lists.

TRİleri seviye öğrenciler için kritik bir ayrım: sistem çağrısı ile kütüphane fonksiyonu aynı şey değildir. printf() bir kütüphane fonksiyonudur; içeride arabelleğe alır (buffering) ve sonunda bir write() sistem çağrısını tetikler. malloc() da bir kütüphane fonksiyonudur; içeride brk() veya mmap() kullanır — ama her malloc() çağrısı bir sistem çağrısına dönüşmez, çünkü glibc küçük ayırma taleplerini kendi iç serbest listelerinden karşılar.

DEEine entscheidende Unterscheidung für Fortgeschrittene: ein Systemaufruf ist nicht dasselbe wie eine Bibliotheksfunktion. printf() ist eine Bibliotheksfunktion, die intern puffert und schließlich einen write()-Syscall auslöst. malloc() ist ebenfalls eine Bibliotheksfunktion, die intern brk() oder mmap() nutzt — aber nicht jeder malloc()-Aufruf wird zu einem Syscall, da glibc kleine Anfragen aus eigenen internen Freilisten bedient.

💡 Tip: a real-world case: a web server slows down under load. Tracing with strace reveals dozens of tiny mmap()/munmap() calls per request — because per-request buffers exceed glibc's mmap_threshold (128 KB by default), so each allocation goes straight to the kernel. Fix: pool and reuse buffers, or tune the threshold with mallopt().
💡 İpucu: gerçek dünya vakası: bir web sunucusu yük altında yavaşlıyor. strace ile izlerken, her istek için onlarca küçük mmap()/munmap() çağrısı görülür — çünkü istek başına ayrılan buffer'lar glibc'nin mmap_threshold değerini (varsayılan 128 KB) aşıyor ve her ayırma doğrudan çekirdeğe gidiyor. Çözüm: buffer'ları havuzlayıp yeniden kullanmak ya da eşiği mallopt() ile ayarlamak.
💡 Hinweis: ein Praxisfall: ein Webserver wird unter Last langsamer. strace zeigt Dutzende winziger mmap()/munmap()-Aufrufe pro Anfrage — weil die Puffer pro Anfrage glibcs mmap_threshold (Standard 128 KB) überschreiten und jede Allokation direkt zum Kernel geht. Lösung: Puffer poolen und wiederverwenden oder den Schwellenwert mit mallopt() anpassen.

The kernel developer's world is inverted: no libc, no malloc(), no signal handlers. Kernel code uses its own toolkit — kmalloc()/kfree() for allocation, printk() for logging, spinlocks and mutexes for synchronization. Code running in interrupt context cannot sleep, must assume it cannot take a page fault, and must treat every byte from user space as suspect — which is exactly why safe-copy functions like copy_from_user() exist.

TRÇekirdek geliştiricisi için dünya tersine döner: artık libc yoktur, malloc() yoktur, sinyal işleyicileri yoktur. Çekirdek kodu kendi araç setini kullanır: bellek ayırma için kmalloc()/kfree(), günlükleme için printk(), senkronizasyon için spinlock ve mutex. Kesme bağlamında (interrupt context) çalışan kod uyuyamaz, sayfa hatası alamayacağı varsayımıyla yazılmalıdır ve kullanıcı alanından gelen her veriye şüpheyle yaklaşmalıdır — copy_from_user() gibi güvenli kopyalama fonksiyonlarının var olma sebebi tam olarak budur.

DEDie Welt des Kernel-Entwicklers ist umgekehrt: keine libc, kein malloc(), keine Signal-Handler. Kernel-Code nutzt sein eigenes Werkzeugset — kmalloc()/kfree() zur Speicherzuteilung, printk() zum Loggen, Spinlocks und Mutexe zur Synchronisation. Code im Interrupt-Kontext darf nicht schlafen, muss davon ausgehen, dass er keinen Page Fault erhalten darf, und muss jedes Byte aus dem User Space als verdächtig behandeln — genau deshalb existieren sichere Kopierfunktionen wie copy_from_user().

performans The Real Cost of a Ring Transition — Ring geçişinin somut maliyeti— Die tatsächlichen Kosten eines Ringwechsels

A ring 3 → ring 0 transition is not "free." On a modern x86-64 CPU, an empty system call (like getpid(), which does almost no work) typically costs 100-300 nanoseconds via the SYSCALL/SYSRET pair — versus under 1-2 nanoseconds for a plain user-space function call. That's up to two orders of magnitude slower, which is exactly why hot-path syscalls get special engineering attention.

TRRing 3'ten ring 0'a geçiş "ücretsiz" değildir. Modern bir x86-64 işlemcide boş bir sistem çağrısının (getpid() gibi, neredeyse hiç iş yapmayan bir çağrı) SYSCALL/SYSRET çifti üzerinden maliyeti tipik olarak 100-300 nanosaniyedir — buna karşılık saf bir kullanıcı alanı fonksiyon çağrısı 1-2 nanosaniyeden azdır. Bu, iki kat büyüklük mertebesine varan bir yavaşlamadır — sık tekrarlanan (hot path) sistem çağrılarının performans mühendisliğinde özel ilgi görmesinin sebebi tam olarak budur.

DEEin Übergang von Ring 3 zu Ring 0 ist nicht "kostenlos". Auf einer modernen x86-64-CPU kostet ein leerer Systemaufruf (wie getpid(), der fast nichts tut) über das SYSCALL/SYSRET-Paar typischerweise 100-300 Nanosekunden — gegenüber unter 1-2 Nanosekunden für einen reinen User-Space-Funktionsaufruf. Das ist eine bis zu zwei Größenordnungen langsamere Operation — genau deshalb bekommen häufig aufgerufene ("hot path") Syscalls besondere Performance-Aufmerksamkeit.

The 2018 Meltdown vulnerability made this worse: the Kernel Page Table Isolation (KPTI) mitigation added a separate page table switch (with partial TLB flush) to every ring transition, increasing the cost by 5-30% for some workloads — a concrete, measurable example of the security-vs-performance engineering trade-off.

TR2018'de ortaya çıkan Meltdown açığı bu maliyeti daha da artırdı: Kernel Page Table Isolation (KPTI) yaması, her ring geçişine ayrı bir sayfa tablosu geçişi (kısmi TLB boşaltma dahil) ekleyerek bazı iş yüklerinde maliyeti %5-30 oranında artırdı — güvenlik ile performans arasındaki mühendislik dengesinin somut, ölçülebilir bir örneği.

DEDie 2018 aufgedeckte Meltdown-Schwachstelle verschärfte das: Die Kernel Page Table Isolation (KPTI) fügte jedem Ringwechsel einen separaten Seitentabellenwechsel (mit teilweisem TLB-Flush) hinzu und erhöhte die Kosten bei manchen Workloads um 5-30% — ein konkretes, messbares Beispiel für den Zielkonflikt zwischen Sicherheit und Performance.

proje 1/3 Observe the Process Table — süreç tablosunu gözlemle— die Prozesstabelle beobachten

The kernel's process-management responsibility has a direct user-space footprint: ps. Run ps aux and redirect the output into a file named surecler.txt in your home directory. Then use grep to find the line for the process named worker and save just that line into worker-satiri.txt.

TRÇekirdeğin süreç yönetimi sorumluluğunun kullanıcı alanındaki doğrudan izdüşümü: ps. ps aux komutunu çalıştır ve çıktısını ev dizininde surecler.txt adlı dosyaya yönlendir. Sonra grep ile worker adlı sürecin satırını bul ve sadece o satırı worker-satiri.txt'ye kaydet.

DEDie Prozessverwaltungsaufgabe des Kernels hat einen direkten User-Space-Fußabdruck: ps. Führe ps aux aus und leite die Ausgabe in eine Datei namens surecler.txt in deinem Home-Verzeichnis um. Finde dann mit grep die Zeile für den Prozess worker und speichere nur diese Zeile in worker-satiri.txt.

proje 2/3 Terminate a Runaway Process — aşırı yük yapan süreci sonlandır— einen außer Kontrolle geratenen Prozess beenden

Suppose worker (PID 512) is consuming too much CPU. First run ps aux to confirm its PID, then terminate it with kill 512. Finally, run ps aux again and save the output into sonra.txt — it should no longer contain a line for worker.

TRDiyelim ki worker (PID 512) çok fazla CPU tüketiyor. Önce ps aux ile PID'sini doğrula, sonra kill 512 ile sonlandır. Son olarak tekrar ps aux çalıştırıp çıktısını sonra.txt'ye kaydet — artık worker için bir satır içermemeli.

DEAngenommen worker (PID 512) verbraucht zu viel CPU. Bestätige zunächst mit ps aux seine PID, beende ihn dann mit kill 512. Führe abschließend erneut ps aux aus und speichere die Ausgabe in sonra.txt — sie sollte keine Zeile für worker mehr enthalten.

proje 3/3 Loadable Kernel Modules in Practice — pratikte yüklenebilir çekirdek modülleri— Loadable Kernel Modules in der Praxis

List currently loaded modules with lsmod and save the output to moduller-once.txt. Load a new module named kk_demo with modprobe kk_demo. Run lsmod again and confirm — using grep — that kk_demo now appears; save that matching line into kk-demo-satiri.txt.

TRlsmod ile o an yüklü modülleri listele ve çıktıyı moduller-once.txt'ye kaydet. modprobe kk_demo ile kk_demo adında yeni bir modül yükle. Tekrar lsmod çalıştırıp grep ile kk_demo'nun artık listede olduğunu doğrula; eşleşen satırı kk-demo-satiri.txt'ye kaydet.

DEListe die aktuell geladenen Module mit lsmod auf und speichere die Ausgabe in moduller-once.txt. Lade mit modprobe kk_demo ein neues Modul namens kk_demo. Führe erneut lsmod aus und bestätige mit grep, dass kk_demo jetzt erscheint; speichere die passende Zeile in kk-demo-satiri.txt.
