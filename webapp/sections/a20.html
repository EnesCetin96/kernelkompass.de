mekanizma LSM: Linux Security Modules — LSM: Linux Güvenlik Modülleri— LSM: Linux Security Modules

The traditional Unix permission model (owner/group/other, read/write/execute, §18) is coarse — a process largely has unlimited authority over files it owns. The LSM (Linux Security Modules) framework places "hooks" at the kernel's critical security-decision points (a file being opened, a socket being created, a capability being checked), letting additional security policies be plugged in. The major modules built on this framework: SELinux (NSA-originated, label-based Mandatory Access Control — MAC — where every process and file carries a security context/label and policy defines which interactions between labels are permitted), AppArmor (a path-based, simpler-to-configure MAC system common on Ubuntu and derivatives), and seccomp-bpf (restricts the set of syscalls a process may use via an eBPF program with fine granularity — heavily used by container runtimes to ensure a process inside a container can only use the syscalls it actually needs, terminating or erroring on anything else).

TRGeleneksel Unix izin modeli (sahip/grup/diğer, okuma/yazma/çalıştırma, Bölüm 18) kaba bir modeldir — bir sürecin sahip olduğu dosyalar üzerinde neredeyse sınırsız yetkisi vardır. LSM (Linux Security Modules) çerçevesi, çekirdeğin kritik güvenlik kararı noktalarına (bir dosya açılırken, bir soket oluşturulurken, bir yetenek kontrol edilirken) "kanca (hook)" yerleştirerek ek güvenlik politikalarının eklenebilmesini sağlar. Bu çerçeve üzerine inşa edilen başlıca modüller: SELinux (NSA kökenli, etiket tabanlı Zorunlu Erişim Kontrolü — MAC — sunar; her süreç ve dosya bir güvenlik bağlamı/etiketiyle işaretlenir, politika bu etiketler arasındaki izinli etkileşimleri tanımlar), AppArmor (yol tabanlı, SELinux'a göre daha basit yapılandırılan bir MAC sistemi, Ubuntu ve türevlerinde yaygın), ve seccomp-bpf (bir sürecin kullanabileceği sistem çağrısı kümesini bir eBPF programıyla ince taneli biçimde kısıtlar — konteyner çalışma zamanları, bir konteyner içindeki sürecin sadece ihtiyaç duyduğu sistem çağrılarını kullanabilmesini, geri kalanların sonlandırılmasını ya da hata döndürülmesini sağlamak için yoğun biçimde kullanır).

DEDas traditionelle Unix-Berechtigungsmodell (Eigentümer/Gruppe/Andere, Lesen/Schreiben/Ausführen, §18) ist grob — ein Prozess hat über ihm gehörende Dateien weitgehend unbegrenzte Autorität. Das LSM-Framework (Linux Security Modules) platziert "Hooks" an den kritischen Sicherheitsentscheidungspunkten des Kernels (eine Datei wird geöffnet, ein Socket wird erstellt, eine Capability wird geprüft) und ermöglicht so das Einbinden zusätzlicher Sicherheitsrichtlinien. Die wichtigsten auf diesem Framework aufgebauten Module: SELinux (NSA-Ursprung, labelbasierte Mandatory Access Control — MAC — bei der jeder Prozess und jede Datei einen Sicherheitskontext/Label trägt und die Richtlinie definiert, welche Interaktionen zwischen Labels erlaubt sind), AppArmor (pfadbasiertes, einfacher zu konfigurierendes MAC-System, verbreitet unter Ubuntu und Derivaten), und seccomp-bpf (schränkt die Menge der Systemaufrufe eines Prozesses über ein eBPF-Programm feingranular ein — von Container-Laufzeiten intensiv genutzt, um sicherzustellen, dass ein Prozess innerhalb eines Containers nur die tatsächlich benötigten Systemaufrufe nutzen kann, während alles andere zur Beendigung oder einem Fehler führt).

vaka Real-World Case: "Permission Denied" With Correct Permissions — Gerçek olay örgüsü: izinler doğru ama "Permission denied"— Realer Fall: "Permission denied" bei korrekten Berechtigungen

An administrator finds that a web server trying to read files from a non-standard directory gets "Permission denied" even though the file permissions (ls -l output) look entirely correct. Inspecting journalctl (or audit.log) turns up an AVC (Access Vector Cache) denial record from SELinux — the server process's security context is not authorized by policy to access files outside the standard web-content directories. The fix is either to label the file with the correct SELinux context (chcon/restorecon) or, if the access is legitimate, to define a custom policy module — disabling SELinux entirely (setenforce 0) is never an acceptable production fix, since it removes all MAC protection at once. This case shows that traditional Unix permissions "looking correct" is not sufficient proof of access — MAC layers sitting on top require their own, separate diagnosis.

TRBir yönetici, bir web sunucusunun standart dışı bir dizinden dosya okumaya çalıştığında, dosya izinleri (ls -l çıktısı) tamamen doğru göründüğü halde "Permission denied" hatası aldığını fark eder. journalctl (ya da audit.log) incelendiğinde, SELinux'un bu erişimi engellediğini gösteren bir AVC (Access Vector Cache) denial kaydı bulunur — sunucu sürecinin güvenlik bağlamı, standart web içerik dizinleri dışındaki dosyalara erişim için politika tarafından yetkilendirilmemiştir. Çözüm, ya dosyayı doğru SELinux bağlamıyla etiketlemek (chcon/restorecon) ya da (erişim meşruysa) özel bir politika modülü tanımlamaktır — SELinux'u tamamen kapatmak (setenforce 0) üretim ortamında asla kabul edilebilir bir çözüm değildir, çünkü bu tüm MAC korumasını bir anda kaldırır. Bu vaka, geleneksel Unix izinlerinin "doğru göründüğü" durumlarda bile, üzerine binen MAC katmanlarının ayrı bir teşhis gerektirdiğini gösterir.

mekanizma Memory-Safety Hardening — Bellek güvenliği sertleştirmeleri— Speichersicherheits-Härtung

The kernel contains various hardening mechanisms against memory-safety bugs in its own codebase (buffer overflows, use-after-free — the kernel-internal counterparts of §6's memory-management bugs): KASLR (Kernel Address Space Layout Randomization) — randomizes the kernel's location in memory on every boot, making it harder for an attacker to predict specific kernel structures' addresses in advance; stack canaries/protector — detects stack-overflow attacks with a "guard value" placed before the return address and checked on function return; KASAN/KFENCE (Kernel Address Sanitizer / Kernel Electric Fence) — development and testing tools that catch memory bugs (especially use-after-free and out-of-bounds access) far earlier than they would otherwise surface. The gradual integration of the Rust language into the kernel (the Rust for Linux project) is one of the most significant recent architectural developments, aiming to have the language's own compile-time guarantees (via the borrow checker) eliminate a portion of these memory-safety issues outright — new drivers in particular are expected to ship with far fewer memory-safety bugs than their C equivalents; this is an active, ongoing debate and transition shaping the kernel development ecosystem's future.

TRÇekirdek, kendi kod tabanındaki bellek güvenliği hatalarına (tampon taşması, use-after-free — Bölüm 6'daki bellek yönetimi hatalarının çekirdek içi karşılıkları) karşı çeşitli sertleştirme mekanizmaları içerir: KASLR (Kernel Address Space Layout Randomization) — çekirdeğin bellekteki konumunu her önyüklemede rastgeleleştirerek, bir saldırganın belirli çekirdek yapılarının adresini önceden tahmin etmesini zorlaştırır; stack canaries/protector — yığın taşması saldırılarını, dönüş adresinden önce yerleştirilen ve fonksiyon dönüşünde kontrol edilen bir "koruyucu değer" ile tespit eder; KASAN/KFENCE (Kernel Address Sanitizer/Kernel Electric Fence) — geliştirme ve test aşamasında bellek hatalarını (özellikle use-after-free ve sınır dışı erişim) çok daha erken yakalayan araçlardır. Rust dilinin çekirdeğe kademeli olarak entegrasyonu (Rust for Linux projesi), bu bellek güvenliği sorunlarının bir kısmını dilin kendisinin derleme zamanında (borrow checker ile) engellemesini hedefleyen, son yılların en önemli mimari gelişmelerinden biridir — özellikle yeni sürücülerin C'ye kıyasla çok daha az bellek güvenliği hatasıyla yazılabilmesi vaat edilmektedir; bu, çekirdek geliştirme ekosisteminin geleceğini şekillendiren aktif bir tartışma ve geçiş sürecidir.

DEDer Kernel enthält verschiedene Härtungsmechanismen gegen Speichersicherheitsfehler in seiner eigenen Codebasis (Pufferüberläufe, Use-after-Free — die kernelinternen Gegenstücke zu den Speicherverwaltungsfehlern aus §6): KASLR (Kernel Address Space Layout Randomization) — randomisiert bei jedem Boot die Speicheradresse des Kernels, was es für einen Angreifer schwieriger macht, Adressen bestimmter Kernel-Strukturen im Voraus vorherzusagen; Stack-Canaries/-Protector — erkennt Stack-Overflow-Angriffe mit einem vor der Rückgabeadresse platzierten "Wächterwert", der beim Funktionsrücksprung geprüft wird; KASAN/KFENCE (Kernel Address Sanitizer/Kernel Electric Fence) — Entwicklungs- und Testwerkzeuge, die Speicherfehler (insbesondere Use-after-Free und Out-of-Bounds-Zugriffe) viel früher erkennen, als sie sonst auffallen würden. Die schrittweise Integration der Sprache Rust in den Kernel (das Rust-for-Linux-Projekt) ist eine der bedeutendsten architektonischen Entwicklungen der letzten Jahre und zielt darauf ab, dass die eigenen Compile-Zeit-Garantien der Sprache (über den Borrow-Checker) einen Teil dieser Speichersicherheitsprobleme von vornherein ausschließen — insbesondere neue Treiber sollen mit deutlich weniger Speichersicherheitsfehlern als ihre C-Äquivalente geschrieben werden können; dies ist eine aktive, laufende Debatte und ein Übergangsprozess, der die Zukunft des Kernel-Entwicklungsökosystems prägt.

mekanizma Real-Time Linux: PREEMPT_RT — Gerçek zamanlı Linux: PREEMPT_RT— Echtzeit-Linux: PREEMPT_RT

§3 introduced real-time scheduling classes such as SCHED_FIFO/SCHED_DEADLINE, but these alone are not enough to provide "hard" real-time guarantees (precise, predictable worst-case latency) — in the standard kernel, certain critical sections (especially those held by spinlocks, §12) can be non-preemptible, meaning even a high-priority task can sometimes be delayed unexpectedly. The PREEMPT_RT patch (now largely merged into mainline) converts nearly all in-kernel spinlocks into preemptible mutex-like structures, turns most interrupt handlers into threaded IRQs (§13), and makes near-total preemptibility possible throughout the kernel — a critical capability that allows Linux to be used in industrial automation, robotics, and telecommunications, domains that demand microsecond/millisecond-precision latency guarantees.

TRBölüm 3'te SCHED_FIFO/SCHED_DEADLINE gibi gerçek zamanlı zamanlama sınıflarını görmüştük, ama bunlar tek başına "sert" gerçek zamanlı garantiler (kesin, öngörülebilir en kötü durum gecikmesi) sağlamaya yetmez — standart Linux çekirdeğinde bazı kritik bölgeler (özellikle spinlock ile korunan kısımlar, Bölüm 12) önlenemez (non-preemptible) olabilir, bu da yüksek öncelikli bir görevin bile bazen beklenmedik biçimde geciktirilebileceği anlamına gelir. PREEMPT_RT yaması (artık büyük ölçüde ana çekirdeğe entegre edilmiş durumdadır), çekirdek içindeki neredeyse tüm spinlock'ları önlenebilir (preemptible) mutex benzeri yapılara dönüştürerek, kesme işleyicilerinin çoğunu threaded IRQ (Bölüm 13) haline getirerek, çekirdeğin neredeyse her noktasında önlenebilirliği mümkün kılar — bu, sanayi otomasyonu, robotik, telekomünikasyon gibi mikrosaniye/milisaniye mertebesinde kesin gecikme garantisi gerektiren alanlarda Linux'un kullanılabilmesini sağlayan kritik bir yetenektir.

DE§3 stellte Echtzeit-Scheduling-Klassen wie SCHED_FIFO/SCHED_DEADLINE vor, aber diese allein reichen nicht aus, um "harte" Echtzeitgarantien (präzise, vorhersehbare Worst-Case-Latenz) zu liefern — im Standard-Kernel können bestimmte kritische Abschnitte (insbesondere solche, die durch Spinlocks geschützt sind, §12) nicht präemptierbar sein, was bedeutet, dass selbst eine hochpriorisierte Aufgabe manchmal unerwartet verzögert werden kann. Der PREEMPT_RT-Patch (mittlerweile größtenteils in den Mainline-Kernel integriert) wandelt fast alle Spinlocks im Kernel in präemptierbare, mutex-ähnliche Strukturen um, macht die meisten Interrupt-Handler zu Threaded IRQs (§13) und ermöglicht so eine nahezu vollständige Präemptierbarkeit im gesamten Kernel — eine kritische Fähigkeit, die den Einsatz von Linux in der Industrieautomation, Robotik und Telekommunikation ermöglicht, Bereichen, die Latenzgarantien im Mikrosekunden-/Millisekundenbereich erfordern.

💡 Tip: PREEMPT_RT trades a small amount of average-case throughput for a much lower worst-case latency — a rational trade for a robot control loop, but usually the wrong one for a general-purpose web server chasing maximum requests-per-second.
💡 İpucu: PREEMPT_RT, ortalama durum verimliliğinden küçük bir miktar feda ederek çok daha düşük bir en kötü durum gecikmesi kazandırır — bir robot kontrol döngüsü için rasyonel bir takas, ama maksimum istek/saniye peşindeki genel amaçlı bir web sunucusu için genellikle yanlış tercihtir.
💡 Hinweis: PREEMPT_RT tauscht einen kleinen Teil des durchschnittlichen Durchsatzes gegen eine deutlich niedrigere Worst-Case-Latenz — ein sinnvoller Tausch für eine Robotersteuerungsschleife, aber meist die falsche Wahl für einen allgemeinen Webserver, der maximale Anfragen pro Sekunde anstrebt.

mekanizma io_uring: Redesigning I/O — io_uring: G/Ç'nin yeniden tasarımı— io_uring: Neugestaltung von I/O

The epoll()-based I/O multiplexing model seen in §8 is powerful, but every I/O operation still requires a separate syscall (the ring-crossing cost from §4 is paid every single time). io_uring is a modern interface that fundamentally reduces this cost: two ring buffers are established, shared between application and kernel — a submission queue and a completion queue. The application can batch up I/O requests by writing them into this shared memory and hand off several requests to the kernel with a single syscall (in some configurations, without any syscall at all, via a kernel-side polling thread); completed operations are read back from shared memory similarly. This design drastically reduces both syscall count and data-copy volume, delivering notable performance gains over epoll() for high-performance storage and network applications (databases, high-frequency trading systems), and is regarded as the future of modern Linux I/O architecture.

Bu tasarım, hem sistem çağrısı sayısını hem de veri kopyalama miktarını kökten azaltarak, yüksek performanslı depolama ve ağ uygulamalarında (veritabanları, yüksek frekanslı işlem sistemleri) epoll()'a göre belirgin performans kazanımları sağlar ve modern Linux G/Ç mimarisinin geleceği olarak kabul edilir.

DEDas in §8 gesehene epoll()-basierte I/O-Multiplexing-Modell ist mächtig, aber jede I/O-Operation erfordert weiterhin einen eigenen Systemaufruf (die Ring-Übergangskosten aus §4 werden jedes Mal erneut bezahlt). io_uring ist eine moderne Schnittstelle, die diese Kosten grundlegend reduziert: zwei zwischen Anwendung und Kernel geteilte Ringpuffer werden eingerichtet — eine Submission Queue und eine Completion Queue. Die Anwendung kann I/O-Anfragen bündeln, indem sie sie in diesen gemeinsamen Speicher schreibt, und mehrere Anfragen mit einem einzigen Systemaufruf an den Kernel übergeben (in manchen Konfigurationen sogar ganz ohne Systemaufruf, über einen kernelseitigen Polling-Thread); abgeschlossene Operationen werden ähnlich aus dem gemeinsamen Speicher zurückgelesen. 💡 Tip: io_uring's win comes from batching, not from any single call being magically faster — the more requests an application can queue up before crossing into the kernel, the larger the relative gain over one-syscall-per-operation models.
💡 İpucu: io_uring'in kazancı toplu işlemden gelir, tek bir çağrının sihirli bir şekilde hızlanmasından değil — bir uygulama çekirdeğe geçmeden önce ne kadar çok istek biriktirebilirse, işlem-başına-tek-sistem-çağrısı modellerine göre göreceli kazanç o kadar büyür.
💡 Hinweis: der Gewinn von io_uring entsteht durch Batching, nicht dadurch, dass ein einzelner Aufruf magisch schneller wäre — je mehr Anfragen eine Anwendung bündeln kann, bevor sie in den Kernel wechselt, desto größer der relative Gewinn gegenüber Ein-Syscall-pro-Operation-Modellen.

uygulamalı Lab: Restricting a Program's Syscall Surface With seccomp — Uygulamalı laboratuvar: seccomp ile bir programın sistem çağrısı yüzeyini kısıtlamak— Labor: die Systemaufruf-Oberfläche eines Programms mit seccomp einschränken

seccomp's simple mode (SECCOMP_MODE_STRICT) or its more flexible BPF mode lets a process's usable syscall set be narrowed. As a conceptual example, using the libseccomp library, a filter allowing only read, write, exit, and exit_group can be built like this:

#include <seccomp.h>
void guvenlik_filtresi_kur(void) {
  scmp_filter_ctx ctx = seccomp_init(SCMP_ACT_KILL); /* default: deny and kill */
  seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(read), 0);
  seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 0);
  seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit), 0);
  seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit_group), 0);
  seccomp_load(ctx);
}

Once this filter is installed, if the program attempts a disallowed syscall such as open(), it is terminated instantly. The suggested exercise: install the filter, then add a code path where the program attempts to open a file, and observe how the process is terminated immediately with SIGSYS — this is a hands-on experience of the mechanism underpinning the seccomp-bpf discussion in §20.2, the foundation of container security hardening.

derinlemesine setuid, setgid, Sticky Bit, and Least Privilege — setuid, setgid, sticky bit ve en az yetki pratiği— setuid, setgid, Sticky Bit und Least-Privilege-Praxis

Beyond the standard triple of file permissions (read/write/execute × owner/group/other, §18), three special bits — setuid, setgid, and the sticky bit — change a program's runtime authority and a directory's deletion behavior. The setuid bit set by chmod u+s program makes a program run with the file owner's identity (geteuid()) rather than the real user's identity (getuid()) at execution time — this is why passwd, though run by an ordinary user, can update /etc/shadow: it is a root-owned, setuid binary that temporarily gains root privilege when it runs. setgid applies the analogous mechanism to group identity; applied to a directory (chmod g+s dir), new files created inside inherit the directory's group instead of the creating user's primary group — a technique widely used for shared project directories. The sticky bit (chmod +t dir, as seen on /tmp) guarantees that files in a directory can only be deleted by their own owners, preventing users in a world-writable directory from deleting each other's files.

TRDosya izinlerinin standart üçlüsünün (okuma/yazma/çalıştırma × sahip/grup/diğer, Bölüm 18) ötesinde, üç özel bit — setuid, setgid, ve sticky bit — programların çalışma zamanı yetkilerini ve dizinlerin silme davranışını değiştirir. chmod u+s program ile ayarlanan setuid biti, programın çalıştırıldığında gerçek kullanıcı kimliği (getuid()) yerine dosya sahibinin kimliğiyle (geteuid()) çalışmasını sağlar — passwd komutunun sıradan bir kullanıcı tarafından çalıştırılabilmesine rağmen /etc/shadow dosyasını güncelleyebilmesinin sebebi budur: passwd root sahipli ve setuid bitli bir programdır, çalıştığı anda geçici olarak root yetkisi kazanır. setgid biti benzer bir mekanizmayı grup kimliği için uygular; bir dizine uygulandığında (chmod g+s dizin), o dizinde oluşturulan yeni dosyaların, oluşturan kullanıcının birincil grubu yerine dizinin grubunu miras almasını sağlar — paylaşımlı proje dizinlerinde yaygın kullanılan bir tekniktir. Sticky bit (chmod +t dizin, /tmp'te görüldüğü gibi) ise bir dizindeki dosyaların yalnızca sahipleri tarafından silinebilmesini garanti eder, herkesin yazma izni olan bir dizinde kullanıcıların birbirinin dosyalarını silmesini engeller.

The standard system-audit command find / -perm -4000 -type f 2>/dev/null lists every setuid-bit file on the system; a standard audit step is to compare this list against the distribution's expected default setuid programs and check for anything unexpected — for example, a setuid file a developer left behind after a debugging session (find / -perm -2000 -type f performs the same audit for setgid bits).
