kavram Why a Distro-Specific Chapter? — Neden dağıtıma özel bir bölüm?— Warum ein distributionsspezifisches Kapitel?

Units 1-20 covered the Linux kernel itself — process management, memory, filesystems, security primitives — knowledge that holds true regardless of which distribution sits on top. But nobody administers "the kernel" directly; they administer a distribution, and distributions differ sharply in how they package software, configure services, and enforce security defaults. This unit and the four that follow it (§22-25) each take one widely deployed distribution and show how it turns the kernel-level theory into concrete day-to-day commands — starting with Ubuntu, the distribution this platform's own production server runs on.

TR1-20. üniteler çekirdeğin kendisini ele aldı — süreç yönetimi, bellek, dosya sistemleri, güvenlik ilkelleri — hangi dağıtımın üzerine kurulduğundan bağımsız olarak geçerli bilgiler. Ama kimse doğrudan "çekirdeği" yönetmez; bir dağıtımı yönetir, ve dağıtımlar yazılımı nasıl paketlediği, servisleri nasıl yapılandırdığı ve güvenlik varsayılanlarını nasıl uyguladığı konusunda belirgin şekilde farklılaşır. Bu ünite ve onu izleyen dört ünite (Bölüm 22-25), yaygın olarak kullanılan birer dağıtımı ele alıp çekirdek seviyesindeki teoriyi somut, günlük komutlara nasıl dönüştürdüğünü gösterir — bu platformun kendi üretim sunucusunun üzerinde çalıştığı Ubuntu ile başlayarak.

DEDie Einheiten 1-20 behandelten den Kernel selbst — Prozessverwaltung, Speicher, Dateisysteme, Sicherheitsprimitive — Wissen, das unabhängig von der darüberliegenden Distribution gilt. Aber niemand verwaltet direkt "den Kernel"; man verwaltet eine Distribution, und Distributionen unterscheiden sich stark darin, wie sie Software paketieren, Dienste konfigurieren und Sicherheitsvorgaben durchsetzen. Ubuntu is developed by Canonical Ltd. and is derived from Debian, inheriting its .deb package format and much of its filesystem layout, while adding its own release cadence, default desktop, cloud tooling, and — critically for this chapter — its own security and packaging conventions on top. Ubuntu ships in three editions (Desktop, Server, Core for IoT) that share the same package base; this chapter focuses on Server-relevant, DevOps-facing administration.

TRUbuntu, Canonical Ltd. tarafından geliştirilir ve Debian'dan türetilmiştir — .deb paket biçimini ve dosya sistemi düzeninin büyük kısmını Debian'dan devralırken, kendi sürüm ritmini, varsayılan masaüstünü, bulut araçlarını ve — bu bölüm için kritik olan — kendi güvenlik ve paketleme geleneklerini üzerine ekler. Ubuntu, aynı paket tabanını paylaşan üç sürümde (Desktop, Server, IoT için Core) dağıtılır; bu bölüm Server'a özgü, DevOps'a yönelik yönetime odaklanır.

DEUbuntu wird von Canonical Ltd. entwickelt und leitet sich von Debian ab — es übernimmt dessen .deb-Paketformat und einen Großteil des Dateisystemlayouts, fügt aber eigenen Release-Rhythmus, Standard-Desktop, Cloud-Tooling und — für dieses Kapitel entscheidend — eigene Sicherheits- und Paketierungskonventionen hinzu. Ubuntu wird in drei Editionen (Desktop, Server, Core für IoT) ausgeliefert, die dieselbe Paketbasis teilen; dieses Kapitel konzentriert sich auf serverrelevante, DevOps-orientierte Administration.

mimari The Release Model — LTS, Interim, and HWE — Sürüm modeli — LTS, ara sürümler ve HWE— Das Release-Modell — LTS, Zwischenversionen und HWE

Ubuntu ships a new release every six months, versioned YY.MM (year.month) rather than a marketing number — Ubuntu 24.04 means April 2024. Every fourth release (every two years, always in April of an even year) is a Long Term Support (LTS) release, receiving five years of standard security updates on the main repository, extendable to ten years total via the free-for-personal-use Ubuntu Pro subscription's Expanded Security Maintenance (ESM). Non-LTS "interim" releases receive only nine months of updates and are not recommended for production servers — this is the single most important fact for a DevOps engineer choosing a base image.

TRUbuntu her altı ayda bir, pazarlama numarası yerine YY.AA (yıl.ay) biçiminde sürümlenen yeni bir sürüm çıkarır — Ubuntu 24.04, Nisan 2024 anlamına gelir. Her dördüncü sürüm (iki yılda bir, her zaman çift yılın Nisan'ında) bir Long Term Support (LTS) sürümüdür ve ana depoda beş yıl standart güvenlik güncellemesi alır; kişisel kullanım için ücretsiz olan Ubuntu Pro aboneliğinin Expanded Security Maintenance (ESM) hizmetiyle toplam on yıla uzatılabilir. LTS olmayan "ara" sürümler yalnızca dokuz ay güncelleme alır ve üretim sunucuları için önerilmez — bu, bir DevOps mühendisinin temel imaj seçerken bilmesi gereken en önemli tek gerçektir.

DEUbuntu veröffentlicht alle sechs Monate eine neue Version, versioniert als JJ.MM (Jahr.Monat) statt einer Marketingnummer — Ubuntu 24.04 bedeutet April 2024. Jede vierte Version (alle zwei Jahre, immer im April eines geraden Jahres) ist eine Long Term Support (LTS)-Version und erhält fünf Jahre Standard-Sicherheitsupdates im Main-Repository, erweiterbar auf insgesamt zehn Jahre über das für den persönlichen Gebrauch kostenlose Ubuntu Pro-Abonnement (Expanded Security Maintenance, ESM). Nicht-LTS-"Zwischenversionen" erhalten nur neun Monate Updates und werden für Produktionsserver nicht empfohlen — die wichtigste einzelne Tatsache für einen DevOps-Ingenieur bei der Wahl eines Basisimages.

/etc/update-manager/release-upgrades controls how do-release-upgrade behaves: with Prompt=lts (the server default), an LTS system only ever offers the next LTS, never an interim release in between — a deliberate guard rail so that apt full-upgrade on a production box can never silently jump onto short-lived support.

TR/etc/update-manager/release-upgrades dosyası, do-release-upgrade komutunun davranışını belirler: Prompt=lts (sunucu varsayılanı) ile bir LTS sistemi her zaman yalnızca bir sonraki LTS'i önerir, arada kalan bir ara sürümü asla önermez — apt full-upgrade gibi bir komutun üretim sunucusunu sessizce kısa ömürlü desteğe sürüklememesi için bilinçli konulmuş bir güvenlik bariyeridir.

DE/etc/update-manager/release-upgrades steuert das Verhalten von do-release-upgrade: mit Prompt=lts (Server-Standard) bietet ein LTS-System immer nur die nächste LTS an, niemals eine dazwischenliegende Zwischenversion — eine bewusste Absicherung, damit ein Befehl wie apt full-upgrade eine Produktionsmaschine niemals still und leise in kurzlebigen Support drängt.

💡 Tip: run lsb_release -a or cat /etc/os-release to see the exact codename and support timeline of the box you're on — the first command any DevOps engineer should run on an unfamiliar Ubuntu host.
💡 İpucu: üzerinde olduğun makinenin tam kod adını ve destek zaman çizelgesini görmek için lsb_release -a veya cat /etc/os-release çalıştır — tanımadığın bir Ubuntu sunucusunda bir DevOps mühendisinin çalıştırması gereken ilk komut budur.
💡 Hinweis: führe lsb_release -a oder cat /etc/os-release aus, um den genauen Codenamen und die Support-Zeitleiste der Maschine zu sehen, auf der du dich befindest — der erste Befehl, den ein DevOps-Ingenieur auf einem unbekannten Ubuntu-Host ausführen sollte.

mimari The Package Stack — dpkg, APT, and Repository Trust — Paket yığını — dpkg, APT ve depo güveni— Der Paket-Stack — dpkg, APT und Repository-Vertrauen

dpkg is the low-level package manager: it installs, removes, and queries individual .deb files, but knows nothing about downloading packages or resolving dependencies from the internet. APT (Advanced Package Tool) sits on top of dpkg and adds exactly that — dependency resolution, repository management, and downloading. The modern user-facing command is simply apt (introduced in 16.04), which unifies what used to be split across apt-get and apt-cache into one friendlier interface with progress bars and colored output; apt-get/apt-cache still exist and remain preferred inside scripts because their output format is guaranteed stable across versions, unlike apt's.

TRdpkg düşük seviyeli paket yöneticisidir: tek tek .deb dosyalarını kurar, kaldırır ve sorgular, ama internetten paket indirmeyi ya da bağımlılık çözmeyi bilmez. APT (Advanced Package Tool), dpkg'nin üzerine tam olarak bunu ekler — bağımlılık çözümü, depo yönetimi ve indirme. Modern, kullanıcıya dönük komut basitçe apt'tır (16.04'te tanıtıldı); eskiden apt-get ve apt-cache arasında bölünmüş olanı, ilerleme çubukları ve renkli çıktıyla tek, daha kullanıcı dostu bir arayüzde birleştirir; apt-get/apt-cache hâlâ vardır ve betiklerde tercih edilmeye devam eder çünkü çıktı biçimleri sürümler arasında kararlı kalması garanti edilirken apt'ınki değildir.

DEdpkg ist der Low-Level-Paketmanager: er installiert, entfernt und fragt einzelne .deb-Dateien ab, weiß aber nichts über das Herunterladen von Paketen oder das Auflösen von Abhängigkeiten aus dem Internet. APT (Advanced Package Tool) setzt auf dpkg auf und ergänzt genau das — Abhängigkeitsauflösung, Repository-Verwaltung und Download. Der moderne, nutzerorientierte Befehl ist schlicht apt (eingeführt in 16.04), der das früher auf apt-get und apt-cache aufgeteilte in eine freundlichere Oberfläche mit Fortschrittsbalken und farbiger Ausgabe vereint; apt-get/apt-cache existieren weiterhin und werden in Skripten bevorzugt, da ihr Ausgabeformat versionsübergreifend stabil bleibt, das von apt hingegen nicht.

Repository sources live in /etc/apt/sources.list and /etc/apt/sources.list.d/*.list (or the newer DEB822 .sources format used by default since 24.04). Each entry is cryptographically trusted via a GPG key registered under /etc/apt/trusted.gpg.d/ or /usr/share/keyrings/ — apt update refuses to install from a repository whose release file signature doesn't verify, which is the mechanism that stops a compromised mirror from silently serving trojaned packages. Third-party PPAs (Personal Package Archives, added via add-apt-repository ppa:user/name) extend this trust model to individual maintainers rather than Canonical itself — convenient for getting newer software, but each PPA you add is a new party you are trusting with root-equivalent code execution on your machine.

TRDepo kaynakları /etc/apt/sources.list ve /etc/apt/sources.list.d/*.list içinde bulunur (ya da 24.04'ten beri varsayılan olan yeni DEB822 .sources biçiminde). Her kayıt, /etc/apt/trusted.gpg.d/ veya /usr/share/keyrings/ altında kayıtlı bir GPG anahtarıyla kriptografik olarak güvenilir kılınır — apt update, sürüm dosyasının imzası doğrulanamayan bir depodan kurulum yapmayı reddeder; ele geçirilmiş bir yansının (mirror) truva atlı paketleri sessizce sunmasını engelleyen mekanizma tam olarak budur. Üçüncü taraf PPA'lar (Personal Package Archives, add-apt-repository ppa:kullanici/isim ile eklenir), bu güven modelini Canonical'ın kendisi yerine bireysel bakımcılara genişletir — daha yeni yazılım almak için kullanışlıdır, ama eklediğin her PPA, makinende root-eşdeğeri kod çalıştırma konusunda güvendiğin yeni bir taraftır.

DERepository-Quellen befinden sich in /etc/apt/sources.list und /etc/apt/sources.list.d/*.list (oder dem neueren DEB822-.sources-Format, das seit 24.04 standardmäßig verwendet wird). Jeder Eintrag wird kryptografisch über einen unter /etc/apt/trusted.gpg.d/ oder /usr/share/keyrings/ registrierten GPG-Schlüssel vertraut gemacht — apt update verweigert die Installation aus einem Repository, dessen Release-Datei-Signatur nicht verifiziert werden kann; das ist der Mechanismus, der verhindert, dass ein kompromittierter Mirror still trojanisierte Pakete ausliefert. Drittanbieter-PPAs (Personal Package Archives, hinzugefügt via add-apt-repository ppa:user/name) erweitern dieses Vertrauensmodell auf einzelne Maintainer statt auf Canonical selbst — praktisch für neuere Software, aber jede hinzugefügte PPA ist eine neue Partei, der man root-äquivalente Codeausführung auf der eigenen Maschine anvertraut.

💡 Tip: apt-mark hold <package> pins a package's version so apt upgrade skips it — useful when a newer version of a critical dependency (e.g. your database driver) is known to break your app, until you can test and unhold it deliberately.
💡 İpucu: apt-mark hold <paket> bir paketin sürümünü sabitler, böylece apt upgrade onu atlar — kritik bir bağımlılığın (örn. veritabanı sürücün) yeni sürümünün uygulamanı bozduğu bilindiğinde, sen bilinçli olarak test edip serbest bırakana kadar kullanışlıdır.
💡 Hinweis: apt-mark hold <paket> fixiert die Version eines Pakets, sodass apt upgrade es überspringt — nützlich, wenn bekannt ist, dass eine neuere Version einer kritischen Abhängigkeit (z. B. dein Datenbanktreiber) deine App bricht, bis du sie bewusst testest und wieder freigibst.

mimari Snap — Sandboxed, Auto-Updating Packages — Snap — sandbox'lı, otomatik güncellenen paketler— Snap — sandboxed, automatisch aktualisierte Pakete

Snap is Canonical's own, distro-agnostic package format, running via the snapd daemon that ships by default on Ubuntu. Unlike a .deb, a snap bundles its own runtime dependencies (no "dependency hell" between two apps needing different library versions) and runs inside a sandbox enforced by the same kernel primitives covered in §18 and §20 — namespaces, AppArmor profiles, and seccomp filtering — with a permission model called confinement.

TRSnap, Canonical'ın kendi, dağıtımdan bağımsız paket biçimidir; Ubuntu'da varsayılan olarak gelen snapd daemon'u üzerinden çalışır. Bir .deb'in aksine, snap kendi çalışma zamanı bağımlılıklarını da paketler (iki uygulamanın farklı kütüphane sürümlerine ihtiyaç duymasından kaynaklanan "bağımlılık cehennemi" yoktur) ve Bölüm 18 ve 20'de işlenen aynı çekirdek ilkelleriyle — namespace'ler, AppArmor profilleri ve seccomp filtreleme — zorlanan bir sandbox içinde, confinement (hapsetme) adı verilen bir izin modeliyle çalışır.

DESnap ist Canonicals eigenes, distributionsunabhängiges Paketformat, das über den standardmäßig auf Ubuntu mitgelieferten snapd-Daemon läuft. Anders als ein .deb bündelt ein Snap seine eigenen Laufzeitabhängigkeiten (keine "Dependency Hell" zwischen zwei Apps, die unterschiedliche Bibliotheksversionen benötigen) und läuft in einer Sandbox, die durch dieselben in §18 und §20 behandelten Kernel-Primitiven — Namespaces, AppArmor-Profile und Seccomp-Filterung — erzwungen wird, mit einem Berechtigungsmodell namens Confinement.

Snaps also update themselves automatically and transactionally — each revision is kept on disk as a read-only, immutable squashfs image, so a bad update can be rolled back instantly with snap revert. This is a meaningfully different philosophy from APT's mutable, in-place package files, and it directly parallels the transactional-update ideas that show up again in §23's discussion of Fedora's rpm-ostree. The trade-off: strict-confined snaps sandbox filesystem access, which occasionally surprises users when a snap-installed app can't see files outside its allowed directories without an explicit interface connection (snap connect).

TRSnap'ler ayrıca kendilerini otomatik ve transaksiyonel olarak günceller — her sürüm, salt-okunur, değişmez bir squashfs imajı olarak diskte tutulur, böylece kötü bir güncelleme snap revert ile anında geri alınabilir. Bu, APT'nin değiştirilebilir, yerinde paket dosyalarından anlamlı biçimde farklı bir felsefedir ve Bölüm 23'te Fedora'nın rpm-ostree'si tartışılırken tekrar karşımıza çıkacak transaksiyonel güncelleme fikirleriyle doğrudan paraleldir. Ödünleşim: sıkı hapsedilmiş (strict) snap'ler dosya sistemi erişimini sandbox'lar, bu da bazen bir snap ile kurulmuş uygulamanın açık bir arayüz bağlantısı (snap connect) olmadan izin verilen dizinlerin dışındaki dosyaları göremeyişiyle kullanıcıları şaşırtır.

DESnaps aktualisieren sich außerdem automatisch und transaktional — jede Revision wird als schreibgeschütztes, unveränderliches Squashfs-Image auf der Festplatte gehalten, sodass ein fehlgeschlagenes Update sofort mit snap revert zurückgerollt werden kann. Das ist eine bedeutend andere Philosophie als APTs veränderliche, In-Place-Paketdateien und läuft direkt parallel zu den transaktionalen Update-Ideen, die in §23 bei Fedoras rpm-ostree wieder auftauchen. Der Kompromiss: strict-confined Snaps sandboxen den Dateisystemzugriff, was gelegentlich überrascht, wenn eine per Snap installierte App ohne explizite Schnittstellenverbindung (snap connect) keine Dateien außerhalb ihrer erlaubten Verzeichnisse sehen kann.

💡 Tip: snap list shows installed snaps and their channel (stable/candidate/beta/edge); pin production systems to stable and reserve edge for testing, exactly the same discipline as tracking an LTS over an interim release.
💡 İpucu: snap list kurulu snap'leri ve kanallarını (stable/candidate/beta/edge) gösterir; üretim sistemlerini stable'a sabitle, edge'i test için ayır — tam olarak bir ara sürüm yerine LTS takip etmekle aynı disiplin.
💡 Hinweis: snap list zeigt installierte Snaps und ihren Kanal (stable/candidate/beta/edge); binde Produktionssysteme an stable und reserviere edge fürs Testen — genau dieselbe Disziplin wie das Verfolgen einer LTS statt einer Zwischenversion.

güvenlik AppArmor — Ubuntu's Default Mandatory Access Control — AppArmor — Ubuntu'nun varsayılan zorunlu erişim kontrolü— AppArmor — Ubuntus Standard-Mandatory-Access-Control

§20.2 introduced Linux Security Modules (LSMs) in general and compared SELinux to AppArmor. Ubuntu's choice, specifically, is AppArmor, enabled by default on every stock install. Where SELinux (Red Hat's default, see §23) labels files and processes with security contexts system-wide, AppArmor is path-based: each profile is a plain text file under /etc/apparmor.d/ naming a specific binary and listing exactly which files, capabilities, and network operations it may touch — generally considered easier to read and author than an SELinux policy, at some cost in robustness against certain path-based bypass techniques.

TRBölüm 20.2, Linux Güvenlik Modüllerini (LSM) genel olarak tanıtmış ve SELinux'u AppArmor ile karşılaştırmıştı. Ubuntu'nun özel olarak seçtiği AppArmor'dır, standart her kurulumda varsayılan olarak etkindir. SELinux (Red Hat'in varsayılanı, bkz. vaka Real-World Case: The Silent PPA Version Pin — Gerçek olay örgüsü: sessiz PPA sürüm sabitlemesi— Realer Fall: die stille PPA-Versionsfixierung

A team adds a PPA to get a newer version of a build tool, six months before a production incident. Long after the PPA is forgotten, apt upgrade on a routine maintenance day pulls in a new release from that same PPA — one built against a newer, incompatible library ABI — and a critical service starts crashing on start. The root cause, found via apt-cache policy <package> (which shows exactly which repository a package's currently-installed and candidate versions come from) and apt-cache madison <package> (which lists every available version and its origin), turns out to be that the PPA's priority silently outranked the official archive. The two-layer fix: apt-mark hold the affected package immediately to stop the bleeding, then add a pinning rule under /etc/apt/preferences.d/ so the PPA can never again outrank the official repository for that package — and, longer term, document every PPA a team has ever added, since an unmaintained PPA is exactly the kind of "temporary" decision this book has repeatedly shown to become a forgotten, dangerous default (compare §20.8's forgotten setuid binary).
